## 1. ARCH Family의 핵심 책임

기존 ARCH 정책의 중심은 개발 체계의 **생명주기별 책임 경계**와 **명시적으로 선언된 구성요소 관계**이다. 서로 다른 생명주기를 소유하는 책임은 분리해야 하며, 관계는 파일명·임포트·도구 위치만으로 추론해서는 안 된다. 특정 구성요소가 다른 구성요소를 호출하거나 같은 디렉터리에 있다는 이유로 서로의 정책 권위를 얻지는 않는다.

다음 원칙은 ARCH 원문의 의미를 옮긴 것이지만, 현행 활성 규칙이라는 주장은 아니다.

1. 정책·계획·구현은 별도의 권위 계층이다. 상위 정책을 하위 계획이 변경할 수 없고, 구현이 정책상의 결정을 대신할 수 없다.
2. 분할 가능한 책임은 단일한 소유 경계를 가져야 한다. 책임이 섞인 구현 단위는 편의상 한 영역에 배치하기보다 분리 여부를 검토한다.
3. 구성요소의 `PRODUCT`, `DEVELOPMENT_TOOLING`, `DELIVERY`, `OPERATIONS`, 중립적 계약 책임은 생명주기 의무로 판단한다. 제조 도구, 언어, 파일 형식은 그 자체로 생명주기 소유자를 결정하지 않는다.
4. 재사용 관계, 검증 대상, 소스 위치는 의존성이나 관측 사실일 수 있지만 그 자체가 규범적 소유권은 아니다.
5. 책임을 정확하게 판별할 근거가 없으면 새 책임 또는 권위를 조용히 발명하지 않고 미결정 상태로 남긴다.

## 2. MPD-ARCH-0001 — 개발 아키텍처의 상위 경계

**원문 상태:** `RETIRED.Waiting`; 과거 내용에 있는 전환 목표 `APPROVED.Applying`과 `transition.state: COMPLETE`는 현재 정책 상태가 아니라 이력 데이터다.

### 2.1 생명주기와 관계의 경계

- 독립적으로 지배 가능한 생명주기 책임을 구분하고, 서로 다른 책임이 혼합된 단위는 분리할 수 있도록 정의한다.
- 프로젝트가 선언한 구성요소 간 관계는 **typed / directed** 관계로 관리한다. 관측된 import나 schema 존재만으로 소유권 또는 관계 의도를 새로 확정하지 않는다.
- 같은 Root Family 소속이라고 모든 규칙을 동일한 정책 ID로 합치는 것은 아니다. 실제 책임 응집성 확인이 선행되어야 한다.
- 경계가 미해결인 경우 무근거 편입 대신 실패 또는 사용자 결정 요청을 선택한다.

### 2.2 정책·계획·구현의 권위 분리

- 정책은 의미, 생명주기, 정책 승인 권위를 소유하고, 계획은 계획의 내용·승인·진행·완료를 소유한다. 구현 산출물은 계획 완료를 독자적으로 선언할 수 없다.
- 정책 승인은 계획 생성·계획 승인·실행 허가를 자동으로 부여하지 않는다.
- 계획의 논리 식별자는 브랜치나 실제 저장 경로와 분리된다. 브랜치 생성은 해당 논리 ID로부터 자동 허가되지 않는다.
- 계획 산출물 루트 `developer/planning/`와 실제 세부 경로의 선택을 구분한다. 세부 경로는 승인된 기계 라우팅으로 유일하게 도출될 때만 자동 선택할 수 있으며, 규칙이 없거나 모호하면 차단한다.
- 계획 생성기·경로 알고리즘·실제 스키마 이동은 정책 결정만으로 구현 또는 실행 승인된 상태가 아니다.

### 2.3 패밀리별 정책 스키마 책임

- 과거 계약은 각 Root Family가 자기 정책 레코드의 필드 구조·필수성·자료형·규칙 본문을 소유하도록 했고, 공통 예외는 GOV가 관리하는 정책 상태 의미였다.
- 과거 목표는 `developer/policy/{FAMILY}/validator/`의 Family-local schema와 Go validator였다. 이는 **원문의 목표 구조**이며 현재 구현이 그러하다는 뜻은 아니다.
- `developer/policy/*.yaml`은 YAML, `*.schema.json`은 JSON Schema를 사용한다.
- `src/policy`의 Support Feature 정책과 `developer/policy`의 Developer Policy는 별도 정책 클래스다. 한쪽의 스키마를 가져왔다고 다른 쪽의 규범적 권위를 갖지 않는다.
- 레거시 공용 resolver와 bound 파일을 제거하거나 기존 validator를 변경하는 행위는 별도의 승인된 전환 없이 자동 정당화되지 않았다.
- 현재의 `Public_Structure_Rules`/Family rules 계약과 과거의 Family-local schema 목표 사이에서 **물리적 공유 구조와 규범적 필드 소유권**을 구분하여 재검토해야 한다.

### 2.4 개발 엔진과 배포 제품의 구분

- Support Feature 엔진은 제품 기능의 권위를 소유하고, Go 기반 개발 확장은 Development Tooling이다.
- 개발 확장을 설치 제품에 함께 배포하거나 Consumer 프로젝트에 강제하거나, 설치 제품의 핵심 엔진으로 대체하면 안 된다.
- 원문의 개발 확장 목표 경로는 `.ptsip/engine/developer/`였으나, 실제 배치 여부는 현재 저장소 구현에서 별도 확인해야 한다.

### 2.5 원문에 포함되었지만 ARCH의 고유 책임이라고 단정할 수 없는 요소

`planning` 승인 정당성은 GOV, 계획 목적은 INTENT, 계획 식별 정보는 INFO, 실행 전 차단 판단은 CTRL, 실제 기계 생성은 REAL, 검증 결과 판단은 ASSURE, 정책 변경 영향은 CHANGE 등 **다른 Family와 결합된 책임**을 포함한다. ARCH에 있었다는 사실만으로 이들의 최종 소유권을 ARCH로 가져오지 않는다.

## 3. MPD-ARCH-0002 — 개발 자동화 구현의 책임 도메인

**원문 상태:** `RETIRED.Waiting`.

이 정책은 자동화 파일의 이름이 아니라 **그 구현이 실질적으로 담당하는 책임**을 기준으로 패키지를 분리하려는 것이다.

### 3.1 기본 경계

- 구현 단위마다 정확히 하나의 책임 도메인을 부여하고, 도메인 소유권을 기계적으로 확인할 수 있어야 한다.
- 여러 의미를 담은 catch-all 패키지와 소유자가 없는 공용 구현을 금지하는 방향이었다.
- 책임이 혼합된 파일은 먼저 분리하고 나서 도메인에 편입한다. 기존 도메인에 억지로 의미를 맞추거나 애매한 근사치만으로 편입하지 않는다.
- 새 도메인이 필요하다면 가까운 기존 책임과의 차이·중복·의미 왜곡 위험을 제시하고 사용자의 결정을 받는다. 실제 파일 이동 목록과 이행 순서는 계획의 책임이다.

### 3.2 원문에 등록된 도메인 및 경로

| 도메인 | 원문의 경로 | 의미상 책임 |
| --- | --- | --- |
| BRANCH | `developer/automation/branch/` | 브랜치 통제 |
| RELEASE | `.github/checks/release/` | 릴리스 신원 소비, 빌드·배포 준비 및 게시 실행 오케스트레이션 |
| TEST_MODE | `developer/automation/testmode/` | 테스트 모드 등록 검증, 변경파일 매칭, 실행 모드 선택, 검증 계획 구성 |
| POLICY / BINDING | `developer/automation/policy/binding/` | 정책 해석 및 바인딩 |
| POLICY / LIFECYCLE | `developer/automation/policy/lifecycle/` | 정책 식별·버전·상태 및 materialization 수명주기 |

이 경로는 **퇴역 원문의 선언**이다. 현재 HEAD에 모든 디렉터리가 존재한다거나 해당 선언이 활성 정책이라는 의미는 아니다.

### 3.3 자동화에 허용되지 않은 권위

- TEST_MODE는 `.github/test_modes.yaml`과 프로젝트 프로파일에 선언된 검증 관계를 **소비**할 뿐 원본 소유권·검증 요구사항·등록부 권위를 새로 정의하지 않는다.
- POLICY/BINDING과 POLICY/LIFECYCLE은 같은 상위 경로의 하위 도메인이지만 서로의 의미 권위를 소유하지 않는다.
- Family-local validator의 구현 위치가 다르더라도 다른 Family의 규칙 의미를 재정의할 수 없다.

### 3.4 퇴역한 공용 검증 실행기

원문은 `.github/workflows/tooling-test.yml`의 **과거 공용 실행기 계약(WEC-01~11)**이 폐기됐다고 기록한다. 당시 기존 자동 실행에 대한 성공 증거는 현행 검증 성공의 근거가 아니며, 증거가 없으면 완료 또는 릴리스 준비성을 단정할 수 없다는 뜻이다. 과거 실행기 상태를 **2026-10-30 현재의 워크플로 상태로 추정해서는 안 된다**. 현행 구현 및 검증 계약은 별도로 조회해야 한다.

## 4. MPD-ARCH-0003 — 개발 검증 구현의 책임 도메인

**원문 상태:** `RETIRED.Waiting`; 과거 버전 `0.0`.

- Developer Verification 구현은 검증 목적의 **책임 도메인**별로 분리한다. 파일마다 단일 소유 도메인이 있어야 하며, 경로에서 책임을 기계적으로 식별하는 것을 목표로 했다.
- 검증을 구현한다는 이유로 검증 대상 정책의 규범을 창설할 수 없고, 한 도메인을 검사한다는 이유로 검증 코드의 소유 도메인이 자동 변경되지 않는다.
- 같은 패키지 위치, 호출 관계, 테스트 모드 실행 관계는 소유권 이전 증거가 아니다.
- 혼합 책임은 소유 목록에 등록하기 전에 분리한다. 기존 도메인에 정확히 일치하면 재사용하고, 유사성만 있으면 배제한다.
- 도메인 목록 자체는 `UNRESOLVED`였으며 자동으로 새 목록을 승인하는 것은 금지되었다. 새로운 도메인 후보는 기존 도메인과 책임 경계를 비교한 뒤 사용자가 결정한다.
- 구체적인 테스트 이동, 의존성 그래프, 이행 순서는 정책이 아니라 계획의 책임이다.
- 원문의 `scope_root: developer/tests`는 역사적 선언이다. 현재 테스트 경로와 일치하는지 검토하기 전에는 현행 경로 정책으로 승계하지 않는다.
- `MPD-ASSURE-0001`의 검증 범위·적합성 판단과 결합되지만 ASSURE의 권위를 ARCH가 대신하지 않는다.

## 5. MPD-ARCH-0004 — 신규 정책이 아닌 독립 계약 후보

**원문 상태:** `APPROVED.provisional` (파일 내부의 `Policy_Status.constant`에 표현).

이 문서에는 독립 규칙이 없다(`independent_rule_refs: []`). 규칙의 의미를 복원할 대상이 아니라 **신규 계약 구조를 적용하려는 후보 및 경계 메타데이터**다.

- 목표 범위는 `아키텍처 경계`이다.
- `semantic_rework_required: true`로 선언되어 있으므로 의미 검토를 끝냈다고 볼 수 없다.
- `normative_content_from_retired_policies: FORBIDDEN`이므로, ARCH-0001~0003의 의미를 그대로 새 정책의 규범으로 복제해서는 안 된다.
- 후보가 참조하는 `urn:ptsip:contract:policy:rules:ARCH:v1`과 현재 실제 `ARCH_rules.json`의 `v2`는 다르다.
- 실제 `ARCH_rules.json` v2는 `Policy_Rules`에 `Identity`, `Definition`, `Boundary`, `Evaluation`, `state`, `title`을 요구한다. ARCH-0004의 현재 형태는 이를 만족하지 않으므로 **후보를 곧바로 완성된 신규 계약으로 선언할 수 없다**.

## 7. 신규 기계어 계약 전환의 미해결 충돌

- **권위 승계 충돌:** 퇴역 0001~0003의 규칙 의미를 신규 계약으로 옮기라는 요청과, 신규 후보 0004의 `normative_content_from_retired_policies: FORBIDDEN`는 그대로 병존할 수 없다.
- **계약 버전 불일치:** ARCH-0004는 ARCH 규칙 계약 v1을 참조하지만 실제 규칙 계약은 v2이다.
- **책임 경계 중첩:** ARCH-0001에 GOV, INTENT, INFO, CTRL, REAL, CNTR, ASSURE, CHANGE 등 다른 Family의 책임 정보가 포함돼 있다. 원문 전체를 ARCH로 복사하면 중복 권위가 발생할 수 있다.
- **역사적 경로의 현행성:** `developer/tests`, `developer/automation/`, Family validator 경로, 공용 검증 워크플로의 목표·퇴역 정보는 현행 상태와 별도로 대조해야 한다.
- **실행 승인과 정책 의미:** `transition.state: COMPLETE`, `TR-... SATISFIED`는 이력상의 처리 결과이지 신규 정책과 마이그레이션 실행 허가가 아니다.

### 사용자 선택이 필요한 권위 충돌 처리

| 옵션 | 의미 | 한계 |
| --- | --- | --- |
| KEEP_PRIOR | ARCH-0004의 퇴역 원문 규범 자동 승계 금지를 유지. 분석 결과는 비권위 참고로만 보존 | 기존 의미를 현재 규범으로 새로 채택하려면 별도 승인 필요 |
| KEEP_LATEST | 사용자의 신규 요청을 우선해 퇴역 원문 의미를 신규 계약의 규범으로 승계할 수 있도록 금지 규칙을 변경 | 그대로 옮기면 다른 Family와 중복·이전 폐기 정책의 재활성화 위험 |
| RECONCILE | 자동 승계 금지는 유지하고, 복원한 의미를 **새 독립 규칙 후보**로 재평가한 뒤 사용자 승인된 것만 새 권위로 채택 | 항목별 검토·재분류가 필요 |

**검토 권고:** `RECONCILE`. 이것은 승인을 대체하지 않는다.
