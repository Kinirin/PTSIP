# PTSIP 정책 개혁 — 임시 작업 공간 안내

작성일: 2026-10-17  
성격: **한시적 한국어 자연어 작업 기록**. 정식 정책·장기 Registry·자동화 시스템이 아니다.

## 기본 방향 — 사용자 승인

이곳은 PTSIP의 개발 정책을 새로운 계약과 스키마로 개혁하는 동안 쓰는 **작업별 분산 기록**이다. 모든 진행 상황을 이 `README.md` 한 파일에 몰아넣지 않는다. 별도 중앙 색인, 상태 동기화 서비스, 공용 JSON Schema, 자동 만료 스크립트를 만들지 않는다.

작업의 설계 범위·사용자 결정·확인 지점은 **해당 작업 파일**에 기록한다. **남은 단계, 작업 그룹, 그룹/단계 우선순위와 그룹 소유 세션은 `pending-work.json` 한 곳에 기록한다.** 이는 임시 실행 순서표이며 장기 Registry나 정식 정책 권위가 아니다. 그룹의 `priority`가 낮을수록 먼저 검토하고, 그룹 내부 단계는 개별 `priority` 순서와 사용자 결정 조건을 따른다. `ON_DEMAND` 단계는 필요할 때만 진행한다. 현재 순위는 에이전트가 작업 계획상 정리한 값으로, 사용자 승인 정책을 뜻하지 않는다. 정보가 없으면 추론해 확정하지 말고 미확인으로 남긴다.

현재 별도의 작업 기록은 다음과 같다.

- `contract-schema-review.yaml` — 신규 계약과 검증 스키마 검토
- `developer-policy-families.yaml` — 신규 개발 정책 및 Root Family의 구현 범위
- `legacy-dependency-replacement.yaml` — 폐기 예정 정책과의 의존성 차단·대체
- `pending-work.json` — 작업별 남은 업무 및 기계적 우선순위

이 목록은 **수동 안내**일 뿐, 기계적 색인이나 개별 작업 상태의 원본이 아니다. 새로운 독립 작업은 새 기록 파일로 분리할 수 있다. 해당 작업의 남은 단계는 `pending-work.json`에서 해당 작업 그룹의 세부 단계로 연결한다. 두 파일의 책임을 혼합하거나 같은 남은 작업을 중복 기재하지 않는다. 서로 다른 에이전트는 파일을 쓰기 전에 저장소 최신 상태를 확인하고 충돌을 조용히 덮어쓰지 않는다.

## 임시 작업 중 적용하는 규칙

1. 신규 계약은 `developer/contracts/` 중심으로 설계한다. 기존 정책의 의미는 참고할 수 있으나 사용자 검수 없이 과거 스키마·호출 방식·필드를 새 권위로 자동 채택하지 않는다.
2. 설계 의도와 책임 경계를 먼저 확인한다. 스키마 수정안을 사용자에게 실제 코드로 보여주고, 필드의 목적·자료형·검증 동작·참조 이유를 한국어로 설명한다. 미결정 사항은 사용자가 판단한다.
3. **사용자가 승인한 임시 규칙만** 개혁 과정에서 실행 규칙으로 적용한다. 작업 기록의 제안이나 에이전트 판단을 사용자 승인과 혼동하지 않는다.
4. 다른 작업 환경에서 이어받을 수 있을 만큼의 진행 지점과 간단한 근거만 남긴다. 추적되지 않은 판단을 자동 완성하지 말고 사용자에게 질문한다.
5. 확인 방식은 자유다. 수동 검토·사용자 확인·자동 테스트는 구분해서 적고, 검증하지 않은 내용을 기계 검증 통과로 기록하지 않는다.
6. 정식 정책과 계약에서 임시 기록에 역방향으로 의존하지 않는다. 자세한 적용 범위는 아래 ‘정식 영역의 임시 기록 의존 금지’를 따른다.


## 정식 영역의 임시 기록 의존 금지 — 사용자 승인

`developer/Temporary_Record/`는 **정식 개발 정책이나 계약의 입력·실행 의존성이 되어서는 안 된다.** 이 폴더는 최종 삭제 대상이므로 다음의 **단방향 참조**를 지킨다.

- **허용:** `developer/Temporary_Record/`의 작업 기록이 신규 정책·계약 파일을 경로로 가리키거나, 이전 정책을 비교·검수 자료로 설명하는 것.
- **금지:** `developer/policy/`와 `developer/contracts/` 아래 새로 작성·개정하는 정식 정책, 스키마, Registry, Resolver, 계약 데이터가 임시 폴더의 파일·경로·상태·규칙을 필수 참조하거나 임시 파일의 존재를 전제로 동작하는 것. `$ref`, `import`, 파일 경로, 문서 링크, 실행 스크립트, 검증 입력 등의 형태로 우회 의존성을 만들지 않는다.
- **서술도 최소화:** 정식 파일의 설명·주석·메타데이터에 임시 폴더의 존재를 기록하지 않는 것을 원칙으로 한다. 개혁 과정을 설명해야 한다면 이 임시 작업 기록에 남긴다.
- **정식화 시 독립성:** 임시 기록에서 확정한 내용이 정식 정책으로 채택되면, 사용자가 승인한 의미를 정식 영역에 **독립적인 규칙과 계약으로 다시 작성**한다. 임시 문서를 출처나 권위로 호출하지 않는다.
- **삭제 가능성 유지:** 임시 폴더를 삭제하더라도 정식 정책·계약의 해석, 참조 해소, 검증 및 실행이 이 폴더 때문에 실패하지 않아야 한다.

현재 존재하는 이전 자료의 이력까지 일괄 수정한다는 뜻은 아니다. 정식 파일에 임시 폴더 의존성이 꼭 필요해 보이는 예외 상황을 발견하면 임의로 추가하지 말고 사용자에게 별도 판단을 요청한다.

## 임시 검증 도구의 허용 범위

임시 정책이라고 검증 자체를 금지하지 않는다. 기존 정책 의존성이 제거되었는지, 신규 계약·스키마가 의도대로 작동하는지 확인하는 데 필요한 **임시 스크립트·검증기·테스트 자료·보조 계약·검증용 스키마**는 `developer/Temporary_Record/tools/` 아래에 생성하거나 수정할 수 있다. 검증 목표가 구체적일 때 필요한 만큼만 구현하며, 단순한 검토만 필요한 단계에서 도구를 미리 생성하지 않는다.

임시 도구의 생성·수정은 승인된 개혁 작업의 검증 및 구현에 한정된다. 정식 정책의 권위나 계약 의미를 도구에서 임의로 결정하지 않으며, `developer/contracts/` 또는 `developer/policy/`의 장기적 계약·스키마를 변경하려면 해당 설계와 사용자 승인을 별도로 따른다. 임시 검증기가 존재하거나 통과했다는 사실이 정식 정책의 승인 또는 자동 승격을 의미하지 않는다.

검증용 자산은 임시 경로 내에서만 소유한다. 다른 `developer/` 하위 경로에 임시 도구를 임의로 흩뿌리지 않는다. 특히 정식 정책·계약·장기 CI와 런타임이 이 도구를 필수 입력으로 사용하지 않게 한다. 다른 경로의 임시 산출물이 불가피하다면 사용자에게 먼저 알린다. 임시 도구도 폴더 전체 삭제 시 함께 폐기한다.

## 작업 그룹의 독점 담당과 세션 식별

`pending-work.json`의 `groups`는 기존 단계 간 의존성을 **한 작업 그룹으로 묶은 실행 단위**다. 각 그룹 안에는 독립적인 세부 단계와 우선순위를 유지하지만, **그 그룹의 모든 단계는 한 채팅·작업 세션이 처음부터 끝까지 담당**한다. 서로 의존하는 단계를 다른 에이전트에게 나누어 할당하지 않는다. 그룹 간 독립 작업은 병렬로 진행할 수 있다.

- 소유자 표시는 그룹의 `owner_session_id` **하나만** 사용한다. `null`이면 아직 점유되지 않았고, 값이 있다면 해당 세션이 담당한다. AI 이름·모델·성능·프로필 등은 기록하지 않는다.
- 작업에 착수하는 에이전트는 최신 `pending-work.json`을 읽고, 담당자가 없을 때 **자신의 세션 ID**로 그룹 전체를 점유한다. GitHub의 최신 파일 버전 확인과 충돌 방지 방식으로 변경을 커밋한 뒤에만 해당 그룹을 수정한다.
- 이미 다른 세션 ID가 기록되어 있다면 그 그룹의 내용을 읽을 수는 있어도 **작업·수정·점유 해제·교체는 하지 않는다**. 동시 변경이 감지되면 최신 내용을 다시 읽고, 다른 담당자의 변경을 덮어쓰지 않는다.
- 담당 세션이 작업을 끝내면 점유를 해제할 수 있다. 담당 세션이 중단되거나 사라지면 자동 만료·자동 탈취하지 않으며 **사용자가 재할당 여부를 결정**한다.
- 그룹을 점유해도 정식 정책·스키마 변경의 승인이 생기는 것은 아니다. 개별 단계에서 사용자 결정이 필요한 경우에는 그 결정을 기다린다.
- `priority`는 임시 작업 순서를 제안하는 계획 값이며 사용자 승인 정책은 아니다. 작업 상태(`status`)와 현재 점유(`owner_session_id`)를 혼동하지 않는다. JSON 파일 하나에 여러 그룹이 있으므로 동시 점유 갱신은 최신 버전을 확인하면서 재시도한다.

## 종료 원칙 — 부분 만료 없음

임시 규칙과 작업 파일은 최종적으로 **`developer/Temporary_Record/` 폴더 전체와 함께 삭제할 자료**다. 일부 단계가 끝났다는 이유로 규칙이나 파일을 개별 만료시키거나 그 상태를 별도로 검증하지 않는다. 끝나지 않은 단계에 집중하여 전체 대체를 빠르게 완성한다.

장기적 권위는 앞으로 정상화할 `developer/policy/`의 정식 개발 정책이 가진다. 정식 정책이 임시 규칙을 충분히 대체할 수 있는지는 **사용자가 결정**하며, 이를 자동 증명하는 검증기 구현은 필수가 아니다. 물리적인 폴더 삭제 역시 사용자가 명시적으로 요청할 때에만 수행한다.

이 안내는 정식 정책의 승인, 신규 스키마의 유효성, 작업 완료를 증명하지 않는다.
