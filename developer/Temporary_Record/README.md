# PTSIP 정책 개혁 임시 작업 기록

작성일: 2026-10-17  
성격: 정책 개혁 기간에만 사용하는 한국어 자연어 작업 기록  
현재 상태: 진행 중

## 이 기록의 목적

이곳은 PTSIP 개발 정책을 새로운 계약과 스키마 체계로 개혁하는 동안 **다른 작업 환경에서도 현재 작업을 이어가기 위한 임시 기록**이다.

주된 목적은 진행 상황, 사용자 승인 임시 규칙, 아직 해결하지 못한 문제, 마지막으로 확인된 작업 지점을 남기는 것이다. 정책 결정의 모든 판단 과정이나 긴 근거를 영구 보존하는 것이 목적은 아니다. 다른 코딩 에이전트가 이미 채택된 구조를 임의로 다시 설계하지 않도록, 필요한 만큼의 결정 취지와 이유는 짧은 한국어로 남긴다.

이 기록은 언젠가 삭제할 임시 자료이다. 정식 개발 정책이나 새 계약 체계를 영구적으로 대신하지 않는다. 이 기록의 내용을 적용하는 것은 사용자가 승인한 임시 규칙에 한정된다. 아직 검토 중인 제안이나 에이전트의 추론을 사용자 승인 결정으로 취급하지 않는다.

## 현재 개혁의 방향과 참조 경계

새로운 계약과 스키마의 설계 기준은 `developer/contracts/` 아래에 새로 구성하는 자료이다. 이곳에 있는 구조는 대부분 사용자 검수를 거쳤지만, `developer/contracts/lifecycle/policy_status.json`과 `developer/contracts/lifecycle/policy_version.json`은 예외이며 신규 설계의 승인 기준으로 삼지 않는다.

아래 항목은 이전 정책 체계의 자료로서, 신규 정책을 작성하거나 새 필드의 의미를 결정하는 권위로 자동 적용하지 않는다.

- `developer/policy/approvals/`
- `developer/policy/analysis/`
- `developer/policy/contracts/`
- `developer/policy/policy-resolver-bindings/`
- `developer/policy/legacy/`
- `developer/policy/registries/`
- `developer/policy/schemas/`
- `developer/policy/MPD-BOUND-0001.yaml`
- `developer/policy/policy-resolver-contract.yaml`
- `developer/policy/source-application-review.yaml`
- `developer/state/`
- `developer/verification/`
- `developer/bindings/`
- `developer/contracts/lifecycle/policy_status.json`
- `developer/contracts/lifecycle/policy_version.json`

이전 자료는 필요하면 **참고와 비교를 위해 읽을 수 있다**. 그러나 유용해 보이는 내용도 사용자 검수를 거쳐 **의미만 다시 채택**해야 한다. 이전 필드명·파일 구조·스키마·검증기·의존 관계를 그대로 가져오거나, 아직 없는 새 계약을 이전 구현으로 대신하지 않는다.

이전 자료에는 새 정보를 저장하거나 새로운 정책을 생성하지 않는다. 기존 파일은 사용자가 삭제를 요청할 때까지 보존하며, 임의 삭제·정리·덮어쓰기를 하지 않는다.

`developer/policy/ARCH/`, `GOV/`, `INFO/`, `RECORD/` 등 Root Family별 경로는 앞으로 **신규 계약에 따라 작성할 정식 개발 정책의 대상 영역**이다. 이 목표 경로 자체와 그 안의 기존 또는 폐기 예정 자료를 혼동하지 않는다. 14개 Root Family 체계는 폐기된 것이 아니라 개혁 과정에서 설계를 잠시 중단한 것이다.

## 작업 중 적용하는 사용자 승인 임시 규칙

1. **설계 의도 우선.** 사용자가 무엇을 저장하고 어떤 책임을 분리하려는지부터 확인한다. 잘못되었을 수 있는 기존 스키마의 외형을 무조건 보존하지 않는다.
2. **먼저 설명하고 검수받기.** 스키마와 계약을 제안할 때에는 실제 코드 내용, 데이터 예시, 필드별 목적, 검증 동작, 참조·호환성 및 향후 변경 영향을 한국어로 설명한다. 필드의 의미가 불확실하면 임의로 확정하지 않고 사용자에게 질문한다.
3. **기존 의존성 자동 복구 금지.** 새 계약이 없거나 호출 방법이 불명확하다는 이유로 폐기 예정 Resolver·Registry·스키마·검증기로 되돌아가지 않는다.
4. **사용자 승인과 제안 구분.** 사용자가 승인한 임시 규칙은 개혁 작업 중 적용할 수 있다. 에이전트가 제안한 내용은 승인되기 전까지 작업 권위가 아니다. 기존 또는 신규의 다른 결정과 충돌하면 어느 쪽도 조용히 덮어쓰지 않고 사용자에게 판단을 요청한다.
5. **진행 기록 중심.** 모든 설계 이유를 기계 계약으로 만들거나 매 단계에 장문의 설명을 의무화하지 않는다. 다른 환경의 에이전트가 방향을 오해하지 않을 정도의 짧은 근거는 남긴다. 그 설명으로도 납득하기 어렵다면 에이전트가 독단적으로 재설계하지 말고 사용자에게 물어본다.
6. **검증을 과장하지 않기.** 마지막으로 확인한 작업 지점은 남기되, 이를 반드시 전용 검증기나 자동화 스크립트로 증명할 필요는 없다. 사용자 확인, 문서 검토, 실제 테스트를 서로 구분해서 기록하고, 실행하지 않은 검사를 통과했다고 쓰지 않는다.
7. **다른 환경의 변경 보호.** 작업을 시작하거나 갱신하기 전에 저장소의 최신 내용과 다른 환경의 진행 기록을 다시 확인한다. 서로 호환되지 않는 사용자 결정이 발견되면 최신이라는 이유만으로 한쪽을 선택하지 않고 충돌을 알린다. 기존 작업 기록을 무작정 덮어쓰지 않는다.

## 임시 규칙의 만료 방식

임시 규칙은 장기적 개발 정책 권위를 계속 유지하기 위한 것이 아니다. 정식 `developer/policy/` 정책이 해당 임시 기록의 역할을 대체할 수 있게 되면, **사용자가 대체 가능 여부를 결정**한다. 자동 검증기나 스크립트가 대체 가능성을 증명할 의무는 없다.

한 기록에 여러 규칙이나 단계가 있더라도 **개별 규칙만 따로 만료하지 않는다**. 일부 작업이 먼저 끝나면 개별 만료 상태·부분 만료 근거·부분 검증 절차를 추가하는 대신 **남아 있는 작업을 우선적으로 완료하는 데 집중**한다. 모든 역할의 대체가 준비되고 사용자가 전체 대체를 결정했을 때에만 임시 기록 전체를 한 번에 만료한다. 아직 남은 역할이 있는데 전체를 조기 만료하는 것도 금지한다.

만료 결정과 실제 파일 삭제는 구분한다. 기존 자료 또는 이 임시 파일의 물리적 삭제를 지금 승인한 것은 아니며, 삭제는 사용자가 별도로 요청할 때 수행한다.

## 현재 확인된 진행 지점 (2026-10-17)

- 사용자는 신규 정책 계약과 검증 스키마를 `developer/contracts/` 중심으로 재설계하고 있다.
- `Authority`, `Policy_Identity`, `Policy_Rules`, `Policy_Status`의 하위 설계 의도와 자료형은 아직 차례로 검토해야 한다. 이 기록이 해당 스키마의 승인이나 완성을 의미하지 않는다.
- `developer/Temporary_Record/`는 작업 진행 기록 중심으로 운영하고, 최소한의 결정 이유만 한국어 자연어로 남기기로 했다.
- 임시 규칙은 사용자 승인 후에만 적용하고, 정식 개발 정책이 대체할 준비가 되면 사용자 판단을 거쳐 기록 전체 단위로 만료하기로 했다.
- 작업 환경 재개에는 사용자 결정, 미결정 문제, 확인된 진행 지점이 필요하지만 전용 상태 관리 모듈이나 검증 자동화를 의무화하지 않기로 했다.
- 이번 기록 작성 자체는 사용자가 저장소 반영을 승인했다. **신규 정식 스키마·정책 변경, 기존 자료 삭제 및 검증 자동화 구축까지 일괄 승인한 것은 아니다.**
- 현재 남은 주요 작업은 각 신규 스키마의 책임·데이터 형태·허용값·참조 규칙을 사용자와 함께 검토하는 것이다. 신규 스키마 검증 전체가 통과했다는 확인은 없다.

## 이후 작업을 이어받는 에이전트에게

먼저 이 기록으로 임시 개혁 범위와 진행 지점을 파악한 다음, 실제로 다룰 `developer/contracts/` 파일의 최신 내용을 읽는다. **이 기록의 요약만으로 파일의 현재 내용이나 검증 성공을 가정하지 않는다.**

새로운 결정을 내리기 전에 해당 사항이 이미 사용자 승인된 것인지, 아직 논의 중인지, 단순히 과거 자료에 있던 내용인지 구분한다. 판단 근거가 부족하면 사용자가 다시 설계 의도를 설명할 수 있도록 질문한다. 작업이 진전되면 아래 항목만 간결하게 갱신하면 충분하다.

- 지금 다루는 계약 또는 정책의 경로와 목적
- 사용자 승인 결정 및 짧은 이유
- 아직 결정되지 않았거나 충돌하는 문제
- 마지막으로 확인된 작업 지점과 확인 방식
- 전체 대체를 마치기 위해 우선 처리할 남은 작업

불필요한 작업 로그, 개별 규칙의 만료 상태표, 상세 자동화 스크립트 사용 문서를 이곳에 쌓지 않는다. 이 문서가 존재한다는 것만으로 새 정책의 JSON Schema 적합성이나 정책 의미의 정당성이 증명되지는 않는다.
