# 2026-11-01 RECORD 개정 입력과 후속 지원 기능 검토

이 파일은 사용자의 자연어 선언을 개정 작업에 보존하기 위한 비규범적 검토 기록이다. 개발 정책 원본, Support Feature 정책, 결정 기록 서비스 계약이나 실행 허가를 대신하지 않는다. 이전 번역본 `RECORD-review.ko.md`는 개정 전 상태의 해설이며 이번 새 선언의 규범적 원본으로 사용하지 않는다.

## 이번 개발 정책의 책임 분리

- RECORD 총괄: Family의 책임·역할·하위 문서 경계를 설명하여, 사용자와 AI 에이전트가 모호한 정책 분류에서 적합한 Family를 검토·추천할 수 있도록 한다. 개별 기록 규칙을 총괄 문서에 모두 집중시키지 않는다.
- 정책 결정 기록: 정책문서에 관한 사용자의 정책 결정 기록을 다룬다.
- 작업 계획서 결정 기록: 작업 계획서 문서에 관한 결정 기록을 별도 정책으로 다룬다. 정책과 계획의 경계를 없애거나 한쪽의 기록 규칙을 다른 쪽에 자동 상속시키지 않는다.
- 릴리스 노트 기록: Package·엔진별 기록 파일, 영역, 검증기와 구성 계약의 위치를 별도 정책으로 다룬다.

기존 `MPD-RECORD-0002`의 “독립 규칙 계약 후보” 내용은 삭제한다. 사용자는 후속 답변에서 `0002`의 재사용을 명시적으로 허용했다. 번호를 재사용해도 과거 후보의 계약 v1·권위·상태·내용을 승계하지 않는다.

사용자는 후속 답변에서 네 문서의 목표 상태를 모두 `APPROVED.Unresolved`로 명시했다. 실제 문서는 `developer/policy/RECORD/MPD-RECORD-0001.yaml`부터 `0004.yaml`까지 책임별로 작성했다. 이 상태 지정은 아직 미확정인 결정 기록 schema·바인딩·세부 검증 절차를 확정하거나 소비자 지원 기능을 활성화한 것으로 해석하지 않는다.

## 후속 Support Feature 작업으로 보존한 선언

사용자는 이번에는 RECORD 개발 정책만 작성하고, 소비자 지원 기능 선언은 후속 작업으로 보존하도록 선택했다. 다음 항목은 사용자 저장소를 위한 제품 기능으로 활성화하지 않으며, 지원 기능 정책의 소유 경로와 계약을 별도로 확인한 뒤 다룬다. 같은 개념이 개발 정책의 책임 범위로 기술되더라도 그것이 소비자 기능 권위나 구현 완료를 뜻하지 않는다.

### 저장 위치와 기본 방식

사용자는 정책 결정을 정책문서 자체에 기록하거나 별도 기록 파일에 저장할 수 있다. PTSIP의 저장 위치 선택 기능을 구상하며 기본 저장 위치는 정책문서다. 정책문서 안에 기록할 때는 정형화된 기록 계약을 사용하고 사용자가 만든 계약의 구조와 정체성을 침해하지 않으며 최소 변경을 원칙으로 한다.

### 공통 계약만 있는 저장소

공통 계약 구조에 정책 결정 기록 schema 참조를 연결한다. 사용자 계약 파일과 구별되는 별도 schema 파일을 기본으로 생성한다. 사용자가 원하면 병합할 수 있다. 사용자 계약 자체는 참조 연결에 필요한 최소 범위로 변경한다.

### 독립 계약만 있는 저장소

각 독립 계약의 역할과 책임을 분석하여 정책 결정 기록이 필요한 계약에만 schema 참조를 추가한다. 기록 때문에 정책의 공통 상위 계약을 억지로 생성하지 않는다. 기본 권장은 여러 독립 계약이 하나의 정책 결정 기록 schema를 참조하는 방식이다. 이 schema는 하위 서비스 계약이므로 공유한다는 사실만으로 공통 정책 계약 구조가 생겼다고 판정하지 않는다. 사용자가 원하면 독립 계약별 결정 기록 schema를 둘 수 있다.

### 공통·독립 계약이 함께 있는 저장소

정책 내용을 담당하는 필드의 실제 소유 위치를 확인한다. 공통 계약에 그 필드가 있으면 공통 계약에서 기록 schema를 참조한다. 그 필드가 독립 계약에만 있으면 필요한 독립 계약에서 참조한다. 공통 계약이라는 이유만으로 불필요한 바인딩 계층을 추가하지 않는다. 이 경우 하나의 서비스 schema를 참조하는 방식을 강하게 권장하고 독립 계약마다 별도 결정 기록 구조를 만드는 방식은 비권장한다. 다만 역할·책임상 필요하지 않은 모든 독립 계약에 참조 연결을 강제하지 않는다.

### 정책문서와 결정 기록을 분리하는 저장소

- 결정 기록 schema 계약의 예정 위치는 `.ptsip/contracts/Decision_Record/policy/`와 `.ptsip/contracts/Decision_Record/plan/`으로 분리한다.
- 정책 결정 기록 데이터는 `.ptsip/context/`에 둔다.
- 사용자 정책 계약의 schema에는 필요한 바인딩 참조를 연결한다. 정책 결정 연결에는 경로와 SHA256 패턴의 고유 ID가 필요하다.
- 결정 상세 내용은 지정된 기록 파일에 작성한다. 정책문서에는 결정 내용을 식별하기 위한 짧은 상수 이름을 표시한다.
- 상수 이름은 사용자 편의를 위한 식별 보조다. 이름이 충돌하거나 상세 내용을 담지 못할 수 있으므로 그 이름에서 결정 의미를 추론하지 않는다. 실제 판정은 ID로 연결된 결정 기록의 내용을 확인하여 수행한다.
- 기록 분리에는 기록 자체의 검증과 정책에서의 참조 규칙이 필요하다. 필드명, 정확한 record·binding schema, 무결성 계산 방식과 검증 절차를 이번 입력만으로 임의 완성하지 않는다.

작업 계획서 기록의 상세 보관·바인딩·검증 규칙은 정책 결정 규칙에서 자동 복사하지 않는다. 별도 선언이 부족한 부분은 미결정으로 보존하고 충돌·문제가 생기면 사용자에게 재검토를 요청한다.

## 개발 릴리스 노트에 대해 확정한 내용

- Package 노트 패턴: `docs/releasenote/PTSIP_Package/{package_version}.md`
- 엔진별 노트 패턴: `docs/releasenote/engine/{engine}/{engine}-engine-{version}.md`
- 여러 엔진의 노트를 하나의 병합 노트 파일로 만드는 것은 금지한다.
- 기록 영역: `tool`, `project-profile`, `PTSIP_Package`, `engine`
- 릴리스 노트 검증 또는 참조 역할을 수행하는 검증기의 위치: `.ptsip/engine/developer/Distribution/release/`
- 릴리스 노트 구성 계약의 위치: `.ptsip/contracts/release/`. 다른 위치를 해당 구성 계약의 원본 위치로 사용하지 않는다.

이전 정책·계획에 섞여 있던 관측 상태·이력·과거 승인을 새 정책에 일괄 승계하지 않는다. 이번 선언에 없는 상세 규칙은 과거 문서나 에이전트 추정으로 보충하지 않는다.
