## 1. Inventory rule

This inventory classifies verification by the correctness responsibility it protects, not by filename, directory, framework, fixture contents, or the PTSIP classification of the test implementation itself.

For this repository:

```text
PTSIP package / distributed Tool behavior
    -> repository Product responsibility
    -> VPMS PRODUCT purpose

repository-only release / CI / migration / maintenance automation
    -> repository Toolchain responsibility
    -> VPMS TOOLCHAIN purpose
```

The verifier implementation remains development-time tooling. A test implemented by a PTSIP `TOOLCHAIN` component may therefore have VPMS purpose `PRODUCT` when it protects the distributed PTSIP Tool.

`MIXED` below is an inventory status for a physical pytest module that contains tests with more than one VPMS purpose. It is **not** a third VPMS purpose. Mixed modules must be split at Verification Case granularity rather than assigned one purpose from their path.

## 4. Inventory conclusions

At the baseline above:

- all `19` existing `tests/ptsip/` pytest modules are inventoried;
- `18` modules are homogeneous `PRODUCT`-purpose verification candidates;
- `1` module is physically mixed and therefore must be represented by multiple Verification Cases;
- the mixed module contains `4` `PRODUCT`-purpose tests and `2` `TOOLCHAIN`-purpose tests;
- no existing test responsibility requires an `UNRESOLVED` note at this baseline;
- there is no evidence supporting a bulk `tests/ptsip/product/` / `tests/ptsip/toolchain/` move;
- current path and filename remain non-authoritative for VPMS purpose.

The small number of current TOOLCHAIN-purpose tests is not a reason to invent more. It reflects the observed repository inventory: most existing tests protect behavior of the PTSIP Tool that this repository produces, while the explicit release/CI workflow assertions protect repository development automation.

## 5. Downstream use

`WU-12` may use this inventory to choose representative real Verification Cases, but it must preserve case-level purpose. In particular:

- a physical pytest module may supply more than one Verification Case when responsibilities differ;
- `test_release_readiness_030.py` must not be registered as one purpose-bound case merely because it is one file;
- shared fixtures or implementation helpers do not imply shared purpose;
- physical test reorganization remains optional and must follow semantic evidence rather than create it.
