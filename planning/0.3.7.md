## 2. Governing profile-transition model

The active canonical repository profile remains:

```text
ptsip.yaml
```

A target draft prepared while the canonical file still represents an older draft uses:

```text
ptsip_<major>.<minor>.<micro>.yaml
```

For this repository, the first self-hosted transition expected by Tool `0.3.7` is:

```text
ptsip.yaml             # currently 0.3.6-draft
    ->
ptsip_0.3.7.yaml       # temporary 0.3.7-draft target
```

The root `ptsip.yaml` MUST NOT be rewritten in place merely to change its draft identity. It remains the migration source until its source-specific Required Work Elements have been completed against the target profile.

After completion and validation:

```text
remove old ptsip.yaml
rename ptsip_0.3.7.yaml -> ptsip.yaml
```

## 3. Canonical migration-control terms

Tool `0.3.7` uses the terms frozen by ADR-0010.

### Temporary PTSIP Profile File

```text
ptsip_<major>.<minor>.<micro>.yaml
```

A temporary working profile for one target draft. The internal `ptsip.version` must match the filename version plus `-draft`.

### PTSIP Required Work Element (`PTSIP 필수작업요소`)

A validly existing repository file/document represented by the source draft's active classified/domain structure and therefore mandatory for source migration completion.

### PTSIP Removal Migration Element (`PTSIP 제거이전요소`)

A source-mentioned element that is no longer validly active in the repository. It is not copied forward merely for preservation and does not contribute to completion.

### PTSIP Asynchronous Work Target (`PTSIP 비동기작업대상`)

A repository file/document not directly included in the source draft's active migration obligation. It may be added after Required Work Elements if requested, but it never substitutes for required migration and never contributes to source-migration completion.

### PTSIP Draft Sequential Work

The controlled state where more than one newer draft target exists or becomes necessary before previous target migration work has completed.

### Final PTSIP Point File

The highest selected target-draft Temporary PTSIP Profile File into which all still-incomplete source generations converge directly.

## 4. Sequential Work rule

Example:

```text
ptsip.yaml          = 0.3.4-draft
ptsip_0.3.6.yaml    = 0.3.6-draft
ptsip_0.3.7.yaml    = 0.3.7-draft
ptsip_0.4.0.yaml    = 0.4.0-draft  # Final PTSIP Point File
```

Required default migration order:

```text
0.3.7 temporary -> 0.4.0 Final Point -> delete completed 0.3.7 temporary
0.3.6 temporary -> 0.4.0 Final Point -> delete completed 0.3.6 temporary
canonical ptsip.yaml -> 0.4.0 Final Point
final validation
remove old canonical ptsip.yaml
rename Final Point -> ptsip.yaml
```

Intermediate deleted profiles are never migration hops. Every remaining source migrates directly to the Final Point.

Each source independently re-evaluates Required Work Elements, Removal Migration Elements, and Asynchronous Work Targets. These categories are not inherited across versions.

Accepted declarations already accumulated in the Final Point are target state, not inherited source-category metadata. Conflicting target deltas fail closed or require explicit project-owner resolution.

## 5. Evidence and authority pipeline

The cancelled Tool `0.3.6.1` pipeline is retained inside the stronger transition state model:

```text
profile-generation inventory
    -> repository facts
    -> candidate discovery
    -> normalized evidence + provenance
    -> source-draft reader
    -> source-specific obligation evaluation
    -> migration analysis
    -> target proposals
    -> Final Point plan
    -> project-owner preview / confirmation
    -> snapshot validation
    -> safe sequential apply
    -> guarded canonical promotion
```

Authority boundary remains:

```text
Evidence != Authority
Inference != Authority
Proposal != Authority
Temporary target existence != Authority

accepted project-owned architecture decision
    -> exact authorized target delta
```

No path heuristic, confidence score, old classification, repository convention, or migration convenience may silently become architecture authority.

### Standing successor auto-entry authorization

The project owner has approved automatic entry of the next pre-created WU after the currently active WU completes.

For Tool `0.3.7`, after a WU reaches and records its completion gate, the successor MAY be changed from `PRE-CREATED / LOCKED` to `ACTIVE` without requesting a separate entry approval, provided that:

1. predecessor completion is recorded;
2. a fresh exact `dev/0.3.7` HEAD is captured and written as the successor's entry baseline;
3. no unresolved project-owner decision, architecture conflict, or explicit confirmation gate remains;
4. the transition does not skip a required predecessor or Specification boundary.

This standing authorization covers **successor WU entry state only**. It does not silently authorize architecture decisions, confirmation-gated mutations, or implementation outside the active WU's defined scope. If a blocking decision exists, the successor remains locked until that decision is resolved.

Each implementation WU must have focused tests. WU-08 owns final full verification.

Minimum scenarios include:

- no temporary profile;
- one valid temporary target;
- filename/internal-version mismatch;
- duplicate logical target identity;
- multiple temporary versions with deterministic Final Point;
- source ordering closest-to-Final first;
- canonical source always last;
- independent element taxonomy evaluation per source;
- Required Work Element incomplete -> no source deletion;
- Removal Migration Element -> no preservation obligation;
- Asynchronous Work Target -> optional/non-contributing;
- target-delta conflict -> fail closed;
- stale source/final-point snapshot -> fail closed;
- completed temporary source deletion;
- final canonical promotion only after all participating sources complete;
- PTSIP repository dogfood transition `0.3.6-draft -> 0.3.7-draft`;
- full `tooling-test.yml` success on the exact branch SHA required for closure.

## 19. Completion boundary

Tool `0.3.7` is complete only when:

- ADR-0010 semantics are represented by the Specification family;
- profile-generation state is deterministic and fail-closed;
- evidence remains non-authoritative;
- supported source drafts are read non-destructively;
- migration obligations are evaluated independently per source;
- Required Work Elements alone define source-migration completion;
- target proposals and Sequential Work ordering are deterministic and reviewable;
- mutation requires preview/confirmation and exact snapshot validation;
- completed temporary sources are removed only after their own completion;
- canonical `ptsip.yaml` is migrated last and promoted only after global convergence;
- repository dogfood, focused tests, full regression, package/distribution verification, and required workflow verification succeed;
- final Tool/Specification revision binding is frozen for release.
