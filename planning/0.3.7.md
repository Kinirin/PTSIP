## 1. Planning replacement

Tool `0.3.7` replaced the cancelled `0.3.6.1` planning family. The retained migration concepts were strengthened with deterministic source-generation discovery, evidence normalization, compatibility readers, explicit migration obligations, deterministic target deltas, and guarded mutation/promotion.

Tool `0.3.7` now also establishes an explicit separation between Tool SemVer and Project Profile contract identity.

## 2. Three independent version identities

PTSIP SHALL treat these as independent axes:

```text
Tool Version
    example: 0.3.7

Project Profile Contract Version
    example: pp.1.01

Project Profile Instance Revision
    immutable revision/content identity of one concrete declaration
```

The following implication is invalid:

```text
Tool 0.3.7
    => Project Profile 0.3.7-draft
```

Likewise, a PP contract change does not require a Tool version change when the same Tool already supports that contract.

ADR-0019 defines the PP namespace:

```text
pp.<major>.<minor>
```

and the governing major rule:

> **Project Profile major version은 governing lifecycle classification의 집합 또는 그 classification semantics가 변경되어 기존 프로젝트의 lifecycle 재분류를 요구할 수 있을 때 상승한다.**

Within one major generation, PP minor changes represent contract-semantic or structural changes such as components, relationships, associated artifacts, policies, and Responsibility Map declaration/authority semantics. Ordinary repository-specific declaration edits remain instance revisions and do not bump the PP contract version.

## 3. Repository self-adoption boundary

Tool `0.3.7` development does not by itself authorize a repository Project Profile migration.

Until the independent PP identity and PP migration layers are implemented and separately authorized, the PTSIP repository remains on its actual historical source identity:

```text
ptsip.yaml
ptsip.version = 0.3.6-draft
ptsip.specification.revision = d6995ed232e845b88d8235b851e80ab54b7804ea
```

The repository MUST NOT create `ptsip_0.3.7.yaml` or rewrite the root profile merely to mirror Tool `0.3.7`.

ADR-0019 identifies the intended current PP contract as `pp.1.01`, but activation of that identity is downstream work. Architecture acceptance, machine-readable identity implementation, migration capability, repository adoption, and Tool release readiness are separate authorities.

## 4. Migration-control model inherited from ADR-0010

The 0.3.7 migration engine retains these core rules:

- evidence and inference are not architecture authority;
- source generations are analyzed independently;
- Required Work Elements alone contribute to source completion;
- Removal Migration Elements have no preservation obligation;
- Asynchronous Work Targets do not contribute to completion;
- accepted target declarations accumulate as target state, not inherited source-category metadata;
- conflicts fail closed or require explicit owner resolution;
- sources converge directly on the selected Final Point rather than chaining through completed intermediate profiles;
- temporary sources may be removed only after verified completion;
- canonical source is handled last;
- promotion requires exact snapshot/global validation;
- mutation is restricted to accepted semantic deltas;
- interruption/recovery remains ledger-bound and fail closed.

Legacy Tool-numbered temporary-profile examples remain historical/fixture mechanics until WU-10 replaces target-generation identity with independent PP identity.

## 5. Evidence and authority pipeline

```text
profile-generation inventory
    -> repository facts
    -> candidate discovery
    -> normalized evidence + provenance
    -> source compatibility reader
    -> source-specific obligation evaluation
    -> migration analysis
    -> target proposals
    -> deterministic plan
    -> project-owner confirmation
    -> exact snapshot validation
    -> safe apply
    -> guarded promotion
```

Authority boundary:

```text
Evidence != Authority
Inference != Authority
Proposal != Authority
Tool release version != PP migration authority
Migration capability != repository adoption authority

accepted project-owned decision
    -> exact authorized target delta / adoption action
```

## 6. Responsibility-segmented WU sequence

ADR-0020 intentionally increases WU count to create narrow debugging and regression ownership boundaries:

```text
WU-01  Draft profile transition state model
WU-02  Candidate-discovery evidence expansion
WU-03  Evidence/provenance normalization
WU-04  Source-draft compatibility readers
WU-05  Migration analyzer and obligation evaluation
WU-06  Target proposals and Final Point plan
WU-07  Preview, safe sequential apply, recovery, promotion
WU-08  Repository Self-Analysis and Package Baseline
WU-09  Independent Project Profile Identity Core
WU-10  Project Profile Compatibility, Migration, and Adoption
WU-11  Tool 0.3.7 Final Regression, Specification Freeze, and Release Readiness
```

The additional WUs are deliberate. Responsibility separation takes priority over minimizing WU count.

At the same time, every WU must retain the long-term-maintainability properties selected by the project owner:

- typed boundaries and state;
- one primary owner for each responsibility;
- explicit compatibility contracts/registries rather than scattered assumptions;
- independent focused verification;
- fail-closed handling of unknown/ambiguous PP identities;
- later WUs consume earlier contracts instead of duplicating them;
- no Tool/PP/version-instance coupling.

## 18. Standing successor auto-entry authorization

The project owner has approved automatic entry of the next pre-created WU after the current WU completes.

Automatic successor entry requires:

1. predecessor completion is recorded;
2. a fresh exact `dev/0.3.7` HEAD is captured as the successor entry baseline;
3. no unresolved owner decision, architecture conflict, or explicit confirmation gate remains;
4. no required predecessor or Specification boundary is skipped.

This authorization covers **entry state only**. It does not automatically authorize implementation, migration, architecture decisions, profile promotion, Specification freeze, or release.

The intended sequence is now:

```text
WU-08 COMPLETE
    -> fresh exact HEAD
    -> WU-09 ACTIVE

WU-09 COMPLETE
    -> fresh exact HEAD
    -> WU-10 ACTIVE

WU-10 COMPLETE
    -> fresh exact HEAD
    -> WU-11 ACTIVE
```

## 19. Verification discipline

Each WU owns focused verification of its own contract.

```text
WU-08
    repository/package baseline

WU-09
    PP identity/parser/schema/identity compatibility

WU-10
    PP semantic compatibility/migration/adoption fixtures

WU-11
    final integration/full regression/package/workflow/release evidence
```

A failure should be assigned first to the narrowest owning WU rather than patched into a later layer.

The 0.3.6 WU-04G gradual purpose/role-based test migration direction remains active: touched/new tests should improve organization incrementally without triggering an unrelated wholesale test migration.

## 20. Tool 0.3.7 completion boundary

Tool `0.3.7` is complete only after WU-11 closes and all of the following are true:

- Tool and Project Profile identities remain independent;
- ADR-0019 PP version semantics are implemented and verified;
- historical profile sources are preserved and explicitly mapped rather than silently relabeled;
- PP compatibility/migration fails closed for unsupported or ambiguous generations;
- project-owner authority remains required for lifecycle reclassification and actual profile adoption;
- repository/package Product ownership is complete and artifact evidence matches it;
- controlled migration/recovery/promotion fixtures pass against the final PP-aware implementation;
- final Tool runtime/package identity is `0.3.7`;
- final Tool Specification revision is immutable and exact-bound;
- complete regression and distribution verification pass at the final exact SHA;
- final self-hosted workflow succeeds at that SHA;
- no Project Profile is bumped merely to mirror Tool `0.3.7`;
- release handoff records Tool identity, PP compatibility, Specification revision, source SHA, and built artifact identity without conflating them.
