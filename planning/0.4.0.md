## 1. 0.4.0 product direction

The central 0.4.0 direction is:

> **PTSIP should not require a coding agent to understand PTSIP in order to satisfy PTSIP.**

Canonical Korean statement retained from the planning discussion:

> **PTSIP를 준수하기 위해 코딩 에이전트가 PTSIP Specification을 다시 공부해야 하는 상황을 최소화해야 한다.**

A second product principle is:

> **PTSIP should reduce questions, not create more.**

Tool `0.4.0` is therefore planned around Generic Conformance / Architecture Remediation rather than merely adding more diagnostics. The intended Tool behavior is to own as much of the journey from a non-conformant or ambiguous repository back to a valid architecture as can be owned without crossing project-owner authority.

The central 0.4.0 question is:

> **Given a non-conformant or ambiguous architecture, how much of the journey back to a valid architecture can PTSIP itself own?**

The intended answer is not "everything" and not "diagnostics only". PTSIP should deterministically own evidence collection, fact derivation, rule evaluation, solution-space reduction, mechanical planning, safe execution where authorized, and postcondition verification. It must escalate only the semantic dimensions that cannot be legally or architecturally resolved from current authority.

## 2. Core authority model

0.4.0 must preserve a hard separation among the following layers:

```text
Evidence
    repository observation
        ↓
Derived Fact
    deterministic fact derived from evidence
        ↓
Normative Constraint
    Specification rule / executable obligation
        ↓
Architectural Intent
    project-owner authority
        ↓
Decision / Authorization
    explicit permitted target state or mutation authority
```

The governing rule is:

```text
Evidence ≠ Derived Fact ≠ Normative Constraint ≠ Architecture Authority
```

Repository evidence must never silently become architecture authority.

Typed implementation should make this boundary difficult to violate. A target shape such as the following is preferred:

```text
Evidence
DerivedFact
Authority
Constraint
Decision
```

The implementation must not permit conceptual shortcuts such as:

```text
Authority.from_evidence(...)
```

Evidence can establish facts. Facts can make constraints applicable. Constraints can eliminate illegal solutions. None of those operations may invent project intent.

## 3. Responsibility split between Tool and project owner

0.4.0 should use the following responsibility split.

### Tool-owned / automatic

- repository evidence collection;
- deterministic fact normalization;
- rule applicability determination;
- normative rule evaluation;
- definitive violation detection;
- legal remediation candidate generation;
- hard-constraint elimination;
- semantic-equivalence and dominance reduction when provable;
- mechanical Project Profile / schema transformations when the target semantics are already decided;
- planning/applying already-decided moves and field changes;
- exact pre-state snapshot validation;
- post-fix verification;
- conformance re-evaluation.

### Project-owner authority required

Owner authority is required only when the remaining decision is genuinely semantic and cannot be derived from existing authority, for example:

- genuinely ambiguous lifecycle purpose;
- multiple architecture-valid semantic target states remain after all provable eliminations;
- destructive or architecture-changing actions require explicit authorization;
- existing declarations conflict and the current authority does not determine precedence.

When escalation is required, PTSIP should summarize the established evidence and facts, show the remaining legal semantic choices, and ask the smallest possible intent question.

## 4. Planned remediation lifecycle

The planned user-facing lifecycle is:

```text
Detect
  ↓
Explain
  ↓
Plan
  ↓
Apply
  ↓
Escalate (only when unresolved authority remains)
  ↓
Verify
```

`Escalate` is not intended to be the default path. It is the explicit boundary reached after deterministic reduction is exhausted.

The planned terminal/decision outcomes are:

```text
DETERMINISTIC
OWNER_INTENT_REQUIRED
EXTERNAL_FACT_REQUIRED
UNSATISFIABLE
TOOL_CAPABILITY_GAP
```

These outcomes must be semantically distinct.

- `DETERMINISTIC`: one semantic target remains among the modeled legal remediation families; mutation authorization is still evaluated separately.
- `OWNER_INTENT_REQUIRED`: more than one legal semantic target remains because project intent is missing.
- `EXTERNAL_FACT_REQUIRED`: a required fact is not available from the repository/current authority and must come from an external source.
- `UNSATISFIABLE`: no legal semantic target remains under current constraints/authority.
- `TOOL_CAPABILITY_GAP`: a legal resolution may exist, but 0.4.0 does not implement the needed operational rule/remediation family.

## 5. No confidence-as-authority

0.4.0 must not use confidence scores as a substitute for authority.

The decision process should instead be modeled as:

```text
Evidence
  ↓
Derived facts
  ↓
Legal semantic solution space
  ↓
Hard-constraint elimination
  ↓
Remaining semantic solutions
```

The governing cardinality rule discussed for 0.4.0 is:

```text
0 remaining
→ UNSATISFIABLE

1 remaining
→ DETERMINISTIC_REMEDIATION
  (authorization remains separate)

2+ remaining
→ ARCHITECTURE_CHOICE_REQUIRED
```

Canonical Korean planning statement:

> **판별이 명확할수록 옵션은 적어지고 판별이 불분명하면 옵션은 늘어납니다.**

The Tool must not turn a heuristic "high confidence" guess into architecture authority. AI or heuristic confidence may help order or explain survivors, but cannot remove a legal semantic option unless there is a proof or hard constraint that eliminates it.

## 6. Solution Space Engine

A central 0.4.0 capability is a Solution Space Engine.

The planned pipeline is:

```text
candidate generation
    ↓
normative elimination
    ↓
architecture-preservation checks
    ↓
semantic equivalence / dominance reduction
    ↓
cost / blast-radius ordering among valid survivors
```

Candidate elimination and candidate ranking must remain separate operations.

### Elimination

A candidate may be removed only when the Tool can establish a reason such as:

- violates a normative constraint;
- conflicts with current explicit authority;
- fails a required precondition;
- is semantically dominated/equivalent in a way that is provable under the modeled remediation family;
- would break a required architecture invariant.

### Ranking

Among surviving valid candidates, the Tool may order them using non-authoritative factors such as implementation cost, reversibility, blast radius, or advisory heuristics.

Ranking must not silently convert into elimination.

## 7. Semantic target state vs physical mutation plan

0.4.0 must explicitly separate semantic decisions from repository edit mechanics.

```text
SemanticRemediationPlan
        ↓
RepositoryChangePlan
```

Multiple physical ways to implement one semantic target must not be presented to the project owner as multiple architecture choices unless the physical differences themselves carry semantic meaning.

Example:

```text
One semantic target state
    ↓
move file A then edit profile
or
edit profile then move file A
```

If both paths produce the same authorized semantic state and preserve safety, they are execution-planning alternatives, not owner architecture choices.

This separation is essential to reducing unnecessary questions.

## 8. Candidate uniqueness must be scoped

0.4.0 must not claim global uniqueness unless its remediation-family model is closed and complete for that rule.

Preferred wording/semantics:

```text
unique among modeled remediation families
```

rather than:

```text
the only possible architecture in existence
```

A single remaining candidate means deterministic remediation only with respect to the Tool's declared solution model and current authority/constraints.

## 9. Determinacy is not mutation authorization

0.4.0 must keep these concepts separate:

```text
Determinacy
    ≠
Mutation Authorization
```

The Tool may be able to prove exactly one valid semantic target and still be prohibited from mutating the repository automatically.

This distinction is handled by the planned Authority Gate.

## 10. Authority Gate

The planned authority decision layer should expose outcomes comparable to:

```text
AUTO_AUTHORIZED
MECHANICALLY_AUTHORIZED
OWNER_CONFIRMATION_REQUIRED
NOT_AUTHORIZED
```

The Authority Gate is evaluated after semantic target determination and before repository mutation.

A deterministic semantic solution does not bypass the Authority Gate.

## 11. Irreversibility-aware execution

The planned execution policy must account for reversibility and semantic impact.

```text
mechanical + reversible
    → auto apply may be allowed

structural but semantic-preserving
    → guarded apply

architecture-semantic
    → owner confirmation

destructive / irreversible
    → stronger confirmation and verification
```

This model should influence execution authorization, precondition strictness, rollback requirements, and postcondition checks.

## 12. Fresh Solve rule

Every remediation attempt must begin from current state.

```text
Current Specification
+ Current Authority
+ Current Repository State
        ↓
Fresh Solve
```

Historical remediation results must never become authority or a candidate-elimination basis.

History may be used later as a non-authoritative optimization hint only after the fresh solution space has been constructed from current inputs.

This prevents previous decisions, stale repository states, or optimization databases from silently constraining a new architecture problem.

## 13. Planner priority order

The 0.4.0 remediation planner should optimize only after correctness and authority constraints are satisfied.

Priority order discussed for the planner:

```text
1. normative correctness
2. authority preservation
3. architecture intent preservation
4. lifecycle separation
5. future consistency
6. reversibility
7. blast radius
8. implementation cost
9. diff size
```

A key principle is:

```text
minimal diff ≠ best architecture
```

The Tool must not prefer a smaller textual diff when it produces worse architecture, weaker future consistency, or muddier lifecycle boundaries.

## 14. Escalation Proof

When owner input is required, PTSIP should produce an explicit Escalation Proof rather than a vague confidence message.

The proof should identify:

- the exact unresolved semantic dimension;
- the surviving semantic candidates;
- candidates already eliminated and the reason for each elimination;
- established repository facts;
- applicable normative constraints;
- authority already available;
- the exact missing authority/intent needed to continue.

The following are not sufficient escalation reasons:

```text
"complex"
"low confidence"
"AI needed"
```

Escalation should be a proof of missing authority, not a statement of model uncertainty.

## 15. AI role: advisory only

AI is planned as an optional advisory layer, not as architecture authority.

AI must not become:

- Specification authority;
- policy evaluator authority;
- architecture intent authority;
- final decision maker;
- a mechanism that silently eliminates valid semantic candidates.

Its acceptable role is:

```text
ambiguity reduction
explanation
candidate comparison
survivor ranking
minimal owner-question drafting
```

A provider-neutral protocol was discussed:

```python
class AdvisoryResolver(Protocol):
    def resolve(self, request: AdvisoryRequest) -> AdvisoryResponse: ...
```

Potential providers include:

```text
human
OpenAI
Claude
Gemini
offline/local advisor
```

An `AdvisoryResponse` never becomes `Authority` automatically.

If a project owner accepts or supplies an answer, the owner answer may become explicit project authority through the normal authority materialization path.

The core remediation engine must work without AI.

## 16. Operational Rule Registry

0.4.0 should not push executable remediation-control structure into `ptsip.yaml` merely because the Tool gained new capabilities.

The intended separation is:

```text
Specification
    = normative correctness

Operational Rule Registry
    = internal executable handling of supported rules

ptsip.yaml
    = project truth / intent / analysis contract
```

A possible internal operational rule contract is:

```text
OperationalRule
    applies(...)
    evaluate(...)
    propose_solutions(...)
    verify(...)
```

Potential metadata:

```text
rule_id
authority_requirement
automation_level
```

The Tool should avoid creating a large secondary policy DSL unless implementation evidence proves one is necessary.

`rule_id` is intended to bridge:

```text
Specification rule
    ↓
Operational Rule Registry
    ↓
detector / evaluator
    ↓
solution-space planner
    ↓
verifier
```

The operational registry implements rules; it does not supersede Specification authority.

## 17. Project Profile surface stability

New Tool capabilities should not automatically expand `ptsip.yaml`.

A new Project Profile field is justified only when the project itself must declare new authority, intent, or analysis-contract information.

The following should generally remain outside Project Profile authority unless a later approved design proves otherwise:

- remediation preference heuristics;
- confidence scores;
- AI-provider state;
- remediation history;
- execution optimization hints;
- internal Tool capability metadata.

The 0.4.0 design should therefore prefer internal Tool registries/contracts over Project Profile schema growth for purely operational capabilities.

The consolidated architecture pipeline discussed for 0.4.0 is:

```text

    ↓

    ↓
```

Each transition should be typed and inspectable.

The long-term objective is that a coding agent or developer can invoke PTSIP and receive a remediation result without having to manually reconstruct the Specification reasoning chain.

## 19. Safe apply and exact-state execution

The planned mutation lifecycle is:

```text
Plan
    ↓
Exact Pre-state Snapshot
    ↓
Authorization
    ↓
Apply
    ↓
Post-state Validation
    ↓
Full PTSIP Conformance
    ↓
Commit / Promotion
```

A stale repository state must invalidate the plan rather than silently rebasing a semantic decision onto different evidence.

Safe Apply must therefore remain snapshot-bound and fail closed.

This extends the exact-state / guarded-apply principles already established in Tool `0.3.7` migration work into generic remediation.

## 20. Verification model for representative rule families

0.4.0 is not intended to operationalize every possible Specification rule in one release.

The release should establish the general remediation framework plus representative complete rule families demonstrating all major decision outcomes.

At minimum, representative tests should cover:

```text
1. deterministic remediation
2. owner-intent-required remediation
3. unsatisfiable remediation
4. tool-capability-gap remediation
```

The objective is to prove the framework end-to-end rather than claim universal rule coverage.

A support matrix may classify each operationalized rule by capabilities such as:

```text
detect / plan / apply / verify

detect / plan / owner-intent / verify

capability gap
```

## 22. 0.4.0 safety invariants

The previously discussed safety set is:

```text
Authority Firewall
Fresh Solve
Architecture > Minimal Diff
Automation Debt control
Escalation Proof
Option Reduction
Irreversibility-aware Execution
```

### Authority Firewall

No evidence, heuristic, AI response, registry convenience field, or historical result may become architecture authority implicitly.

### Fresh Solve

Every new remediation evaluates current Specification + current authority + current repository state.

### Architecture > Minimal Diff

Correct architecture and lifecycle separation outrank textual diff size.

### Automation Debt

The Tool should not create hidden manual interpretation steps that future coding agents must repeatedly rediscover. If a rule is operationalized, its deterministic reasoning should be represented in executable Tool behavior rather than institutional memory.

### Escalation Proof

Escalation must identify the exact missing authority and remaining options.

### Option Reduction

PTSIP should remove provably invalid/redundant options before asking the owner.

### Irreversibility-aware Execution

More destructive semantic actions require stronger authorization and validation.

## 23. Experimental / non-core directions

The following ideas were discussed as experimental or future-facing and must not become hidden core dependencies for 0.4.0.

### Provider-neutral AI advisory

AI may assist with ambiguity reduction while remaining optional and non-authoritative.

### Autonomous LLM architect advisor

An autonomous architecture advisor may be explored only as an advisory surface. It cannot own project intent or silently authorize changes.

### Natural-language Specification synthesis

A possible future flow is:

```text
natural-language intent
    ↓
draft machine-readable policy/specification change
    ↓
validate
    ↓
project-owner approval
    ↓
immutable Specification revision
```

The Tool must not self-authorize its own normative changes.

### Remediation history database

Historical remediation data may provide non-authoritative optimization hints after Fresh Solve. It must never become authority or a reason to eliminate an otherwise legal current candidate.

### Self-modifying policy

Self-modifying policy is discouraged. The Tool may propose a policy/Specification change, but cannot approve or activate that normative change by itself.

## 24. Remediation-family modeling rule

Operational rules should declare which remediation families they know how to model.

This is required for honest determinacy reporting.

Conceptually:

```text
Rule
  ├─ detect applicability
  ├─ derive violation facts
  ├─ enumerate modeled semantic remediation families
  ├─ eliminate illegal families
  ├─ reduce equivalent/dominated families
  ├─ classify remaining cardinality
  └─ verify postconditions
```

If the Tool knows that its family model is incomplete for a case, it should return `TOOL_CAPABILITY_GAP` rather than overclaiming determinism.

## 25. Architecture-preservation rule

When current explicit Project Profile architecture is valid and more specific than coarse discovery evidence, remediation logic must preserve that authority.

This principle was reinforced during pre-0.4.0 test-architecture work when coarse repository candidates such as `tests/**` were found to conflict with already-partitioned explicit responsibility declarations.

Generalized rule:

```text
coarse discovery candidate
    = evidence / candidate

explicit validated Project Profile partition
    = architecture authority
```

The Tool must not use discovery convenience to collapse explicit owner-defined architecture.

## 26. Verification Responsibility and Test Mode foundation inherited by 0.4.0

Before opening `dev/0.4.0`, the repository completed a substantial verification-responsibility and Test Mode foundation. This is development infrastructure inherited by 0.4.0, not a new architecture-authority source.

The governing separation is:

```text
Verification Responsibility
    ≠ Physical Test Location
    ≠ CI Execution Mode
```

Authority/implementation/execution responsibilities are:

```text

    = physical test implementation

.github/test_modes.yaml
    = execution declaration only

    = deterministic selection mechanism
```

The correct direction is:

```text

    ↓

    ↓

    ↓

```

The incorrect direction is:

```text
physical test path
    ↓

```

Watch paths are execution-selection evidence only and must never become architecture authority.

## 28. CI verification strategy inherited by 0.4.0

The pre-0.4.0 repository has begun separating selective Test Mode execution from full exact-SHA qualification.

The invariant to preserve is:

```text
Selective Test Mode success
    ≠ full repository qualification

Full qualification success
    = complete regression + release/build/artifact checks
      + exact-SHA self-hosted/tooling-test success status
```

Selective execution must never weaken the meaning of the full `self-hosted/tooling-test` status.

For 0.4.0 development, focused Test Mode verification should be used for iteration, while full exact-SHA qualification remains a meaningful checkpoint/release boundary.

## 32. Rule execution contract candidates

An operational rule should be able to answer four distinct questions:

```text
Does this rule apply?
What is the current rule outcome?
What legal semantic remedies can this Tool model?
How is the resulting target state verified?
```

Conceptually:

```python
class OperationalRule(Protocol):
    def applies(self, context): ...
    def evaluate(self, context): ...
    def propose_solutions(self, context): ...
    def verify(self, context, target): ...
```

The final implementation may split these responsibilities across narrower protocols if that improves typing/testing.

## 33. Owner-question minimization

When owner input is unavoidable, the Tool should not ask the owner to reproduce Specification analysis.

Bad interaction:

```text
"Which PTSIP rule applies here and what should we do?"
```

Desired interaction:

```text
PTSIP determines all established facts and legal constraints,
eliminates invalid options,
then asks only for the remaining project-intent dimension.
```

This directly supports the 0.4.0 product principle that coding agents and developers should not need to relearn the Specification to comply with it.

## 34. External-fact boundary

Not all unresolved questions are project intent.

0.4.0 should distinguish:

```text
missing project intent
    → OWNER_INTENT_REQUIRED

missing externally knowable fact
    → EXTERNAL_FACT_REQUIRED
```

This prevents owner-authority prompts from being used as a generic fallback for missing technical evidence.

External facts, when supplied, still enter the system as evidence/facts according to their provenance; they do not become project intent unless the owner explicitly declares intent.

## 35. Unsatisfiable state

If every modeled semantic candidate is eliminated by normative constraints and current authority, PTSIP should return an explicit unsatisfiable result.

It must not:

- select the "least bad" invalid architecture;
- ask AI to invent an exception;
- silently weaken a normative constraint;
- reinterpret evidence as new authority.

A policy or Specification change may be proposed as a separate explicitly authorized action, but it is not a remediation under the unchanged current normative state.

## 36. Tool capability gap

`TOOL_CAPABILITY_GAP` is required to keep 0.4.0 honest about partial operationalization.

A capability gap means:

```text
The Tool cannot complete deterministic remediation with its currently implemented rule/remediation model.
```

It does not automatically mean:

```text
The architecture is ambiguous.
The owner must decide.
The repository is unsatisfiable.
```

These states must remain distinguishable in diagnostics and APIs.

## 37. Verification expectations for each remediation feature

Each operationalized rule/remediation family should have focused tests that cover as applicable:

- applicable and non-applicable repository states;
- deterministic fact derivation;
- violation/non-violation outcomes;
- candidate generation;
- hard-constraint elimination reasons;
- survivor cardinality classification;
- authority-gate result;
- stale-snapshot rejection;
- repository mutation plan generation;
- safe apply or guarded refusal;
- postcondition verification;
- no evidence-to-authority conversion;
- no heuristic/AI elimination of legal candidates.

Full repository qualification should remain a checkpoint rather than the primary feedback loop for each unit change.

- operationalizing every PTSIP rule in 0.4.0;
- treating AI as required runtime infrastructure;
- allowing AI to decide architecture intent;
- expanding `ptsip.yaml` with remediation-history/confidence/provider fields;

## 42. Definition of success for the 0.4.0 direction

0.4.0 should be considered successful when a representative non-conformant repository can be processed so that PTSIP itself:

1. discovers the relevant evidence;
2. derives the relevant facts;
3. evaluates the applicable normative rule;
4. enumerates modeled legal semantic remedies;
5. eliminates provably invalid/redundant remedies;
6. determines whether the result is deterministic, owner-intent-required, externally blocked, unsatisfiable, or a Tool capability gap;
7. asks the owner only for genuinely missing architecture intent;
8. converts the accepted semantic target into a safe physical plan;
9. enforces exact-state authorization and stale-state rejection;
10. applies only authorized changes;
11. verifies the post-state automatically;
12. does all of the above without requiring a coding agent to manually study PTSIP Specification reasoning for ordinary supported cases.

That is the intended transition from PTSIP as a policy/conformance tool toward PTSIP as an authority-aware architecture remediation system.
