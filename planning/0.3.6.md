# PTSIP Tool 0.3.6 — Responsibility Map Generalization and Specification Discipline

> **Status:** PLANNED  
> **Target Tool version:** `0.3.6`  
> **Published baseline:** Tool `0.3.5`  
> **Required Specification family before release:** `0.3.6-draft`  
> **Primary goal:** generalize the repository-owned Responsibility Map without forcing migration, make VPMS visible in the normative Specification, and make Specification binding a mandatory release contract.

## 1. 0.3.5 premise carried forward

Tool `0.3.5` intentionally kept the Responsibility Map light. Its root `ptsip.yaml` demonstrates that a repository can declare real Product, Toolchain, and Neutral Contract ownership using the existing component declaration model without first introducing a new Responsibility Map schema.

Tool `0.3.6` builds on that evidence. It does **not** invalidate the current explicit declaration style. Instead, it adds optional standardization and migration paths for repositories that want them.

```text
existing explicit Responsibility Map
    remains valid

optional 0.3.6 migration
    may adopt a supported template
    or a template + project overrides
    or materialize a migrated explicit map
```

No repository is required to replace a working explicit map merely because templates exist.

## 2. Responsibility Map modes

Tool `0.3.6` must support three project-owned modes.

### Explicit

The repository declares the complete Responsibility Map directly, as Tool `0.3.5` does today. This remains the compatibility baseline and is not treated as legacy behavior.

### Template

The repository explicitly selects one supported, versioned Responsibility Map template. A template is never selected by directory-name heuristics.

### Hybrid

The repository selects a supported template and supplies project-owned overrides/extensions. Explicit repository declarations take precedence over template defaults inside the schema-defined override boundary. Ambiguous or conflicting overrides fail closed rather than being guessed.

## 3. Initial supported templates

The first catalog should remain small and useful. Tool `0.3.6` should include at least these common responsibility shapes, with exact stable IDs frozen during implementation:

1. Python package/library;
2. Python CLI/application;
3. mixed Product + Toolchain repository.

Templates standardize responsibility semantics and useful starting declarations. They do **not** make directory names normative, and they do not prevent a repository from using a completely custom explicit map.

Template identities must be versioned or revision-bound so a later PTSIP release cannot silently change the meaning of a previously selected template.

## 4. Migration behavior

Migration is opt-in and preview-first:

```text
inspect existing declarations
    -> propose template/mapping
    -> show semantic and textual diff
    -> maintainer chooses whether to apply
```

Migration must never silently rewrite a repository-owned Responsibility Map.

Two migration outputs should be supported:

- **template-backed migration** — keep a selected template identity and store only required project overrides/extensions;
- **materialized migration** — expand the selected template into a complete explicit project-owned map so runtime template resolution is no longer required.

Migration must preserve project-specific facts such as `purpose`, selectors, lifecycle ownership, shipping/runtime facts, consumers, analysis inputs, release ownership, and compatibility ownership unless the maintainer explicitly changes them.

If the selected template/override model cannot represent the current declaration losslessly, migration must stop and report the unresolved facts instead of dropping them.

## 5. Resolution precedence

Responsibility resolution must be deterministic:

```text
explicit project override
    >
selected template declaration
    >
template default
```

A fully explicit map does not consult template defaults. Template selection must be explicit; PTSIP must not infer it from repository layout, package manager, language, framework, or filenames.

`purpose` remains repository-owned descriptive intent. Tool `0.3.6` standardizes responsibility semantics and migration mechanics without forcing every project to use the same component IDs or purpose strings.

## 6. VPMS becomes Specification-visible

Tool `0.3.5` shipped VPMS while remaining bound to `0.3.4-draft`. Tool `0.3.6` must close the resulting agent-policy gap by creating a new `0.3.6-draft` Specification that normatively records at least:

- VPMS — Verification Purpose Management System;
- PTSIP classification and VPMS verification purpose as separate axes;
- `PRODUCT | TOOLCHAIN` verification purposes;
- Verification Case as the purpose-bound execution unit;
- Formula, Variables, Policy, Target, and Runner separation;
- Formula reuse without purpose collapse;
- PTSIP core MUST NOT depend on VPMS;
- VPMS may consume stable PTSIP metadata through a narrow read-only boundary;
- VPMS PASS does not imply PTSIP CONFORMANT, and PTSIP CONFORMANT does not imply functional verification PASS;
- Responsibility Map template/migration semantics introduced by Tool `0.3.6`.

## 7. Mandatory Specification release contract

Starting with Tool `0.3.6`, release preparation must fail unless all of the following are true:

1. `pyproject.toml` declares the requested Tool version;
2. `src/ptsip/constants.py` binds `SPEC_VERSION` to `<Tool version>-draft`;
3. `SPEC_REVISION` is a full immutable Git commit SHA;
4. the Specification revision exists and is an ancestor of the release source;
5. canonical Specification files exist at that revision;
6. root `ptsip.yaml` binds the same Specification version, source, and revision;
7. `releasenote/spec-<SPEC_VERSION>.md` exists and is non-empty;
8. the exact release-candidate source SHA has passed the required self-hosted verification.

This is a release gate, not a documentation reminder. The pipeline must reject a release that omits the Specification work.

## 8. `AGENTS.md` and `MEMORY.md`

Root `AGENTS.md` and `MEMORY.md` are repository-operational inputs for coding agents.

- `AGENTS.md` defines required working behavior.
- `MEMORY.md` records durable current repository/release/architecture context.
- Neither replaces the normative Specification.
- Agents must read both before planning or modifying the repository.
- Agents must still read `ptsip.yaml` and the bound Specification.

## 9. Self-hosted verification policy

GitHub-hosted Actions usage is constrained. Full repository testing and release-candidate verification must be moved to the single `.github/workflows/tooling-test.yml` workflow in manual self-hosted mode before Tool `0.3.6` verification begins.

Expected runner identity:

```text
DESKTOP-5HCCQIR
```

The self-hosted test workflow must:

- use a self-hosted Windows runner;
- verify `RUNNER_NAME == DESKTOP-5HCCQIR` before repository work;
- require explicit host-ready acknowledgement;
- never run automatically on push, pull request, tag, schedule, or release;
- run the complete pytest/CLI/build/wheel smoke boundary when manually dispatched;
- support release-candidate verification for one exact SHA.

Before any coding agent or maintainer automation dispatches the self-hosted workflow, the user must be told that the runner will be used and must explicitly confirm that the host and PowerShell environment are ready.

The release-preparation workflow may remain GitHub-hosted for lightweight release orchestration, and the PyPI publication workflow may remain GitHub-hosted for Trusted Publishing. They must not duplicate the expensive full test suite once the self-hosted gate is active.

## 10. Non-goals

Tool `0.3.6` does not aim to:

- make a supported template mandatory;
- discard or auto-convert a valid Tool `0.3.5` explicit map;
- infer Responsibility Map mode from paths or repository naming;
- silently overwrite project-owned responsibility facts;
- make template component IDs mandatory for custom repositories;
- collapse PTSIP classification and VPMS verification purpose;
- turn `MEMORY.md` or `AGENTS.md` into normative Specification documents;
- automatically power on or dispatch the self-hosted runner.
