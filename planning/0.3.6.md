> **Required Specification family:** `0.3.6-draft`  
> **Current bound Specification snapshot:** `12e2ccd15634ecb3d0a4195b0f61ac3f620e7540`  
> **Primary goal:** establish primary lifecycle ownership as the canonical PTSIP classification model, activate Responsibility Map v2, safely understand and migrate Tool `0.3.5` profiles without preserving obsolete `TOOLCHAIN` semantics in the new schema, strengthen evidence-driven candidate discovery, and complete a Specification-bound release pipeline.

## 1. Scope consolidation

Tool `0.3.6` absorbs the previously separate candidate-discovery work because stronger evidence is required for safe migration from Tool `0.3.5`.

The release is organized around one dependency chain:

```text
lifecycle ontology
    -> Responsibility Map semantics
    -> canonical schema/runtime
    -> templates/materialization
    -> stronger evidence discovery
    -> legacy reader
    -> migration proposals
    -> preview/apply
    -> dogfood / regression / release
```

Candidate discovery, migration analysis, role inference, relationship inference, and component-split detection are evidence-producing operations. They do **not** become project architecture authority.

## 2. Published Tool 0.3.5 compatibility boundary

Tool `0.3.5` was published with:

```text
PRODUCT
TOOLCHAIN
NEUTRAL_CONTRACT
```

Tool `0.3.6` canonical classifications are exactly:

```text
PRODUCT
DEVELOPMENT_TOOLING
DELIVERY
OPERATIONS
NEUTRAL_CONTRACT
```

`TOOLCHAIN` MUST NOT be emitted as a canonical Tool `0.3.6` classification and MUST NOT remain as an alias in the new classification enum.

Compatibility means:

```text
Tool 0.3.5 profile
    -> legacy reader
    -> existing declaration + repository evidence
    -> lifecycle / role / relationship / boundary proposal
    -> project-owner confirmation
    -> canonical Tool 0.3.6 Responsibility Map
```

Compatibility does **not** mean silently interpreting an old profile as if it already had Tool `0.3.6` semantics.

Legacy fields such as `TOOLCHAIN`, `lifecycle_owner`, `consumers`, `analysis_inputs`, old boundary roots, and untyped dependency-policy edges are migration evidence. They are not automatic canonical mappings.

## 3. Primary lifecycle ownership ontology

`classification` means the **primary lifecycle ownership of a coherent project-owned architectural responsibility**.

Classification MUST NOT be selected solely from file type, directory name, language, framework, executable status, compilation behavior, workflow provider, deployment technology, or whether an artifact is a test.

### 3.1 `PRODUCT`

Product lifecycle responsibility, including:

- Product runtime or user-facing behavior;
- Product distribution content;
- runtime SDK responsibility;
- Product compatibility responsibility;
- Product-owned quality and verification.

Product-specific tests MAY therefore be `PRODUCT`.

### 3.2 `DEVELOPMENT_TOOLING`

Development lifecycle responsibility, including:

- reusable verification/test infrastructure;
- generators and migration tooling;
- lint/static analysis;
- developer CLI;
- repository transformation;
- development environment support;
- local/intermediate development build support.

This is the development-tooling portion of legacy `TOOLCHAIN`, not a universal rename target.

### 3.3 `DELIVERY`

Responsibility for carrying an authoritative release target to a publication/distribution/deployment destination, including:

- authoritative release-unit assembly;
- artifact signing/attestation for handoff;
- package/container publication;
- release promotion;
- deployment automation and deployment-time configuration.

The Product Artifact and its Delivery producer have independent ownership.

### 3.4 `OPERATIONS`

Post-delivery responsibility for keeping an already deployed system healthy, recoverable, maintained, reconciled, and operational, including:

- production-state management;
- health/availability automation;
- backup/recovery;
- incident and maintenance automation;
- ongoing production infrastructure management.

### 3.5 `NEUTRAL_CONTRACT`

A responsibility qualifies only when all are true:

```text
non-executable architectural role
non-owning implementation responsibility
lifecycle/compatibility governance independent from consuming lifecycles
```

Declarative format, `docs/`, `schemas/`, multiple consumers, or lack of executable permission do not establish neutrality by themselves.

## 4. Lifecycle boundary determination

The frozen semantic procedure is:

```text
1. establish project-owned scope
2. identify a coherent responsibility boundary
3. collect evidence with provenance
4. test NEUTRAL_CONTRACT qualification
5. determine governing lifecycle obligation
6. test for material mixed-lifecycle responsibility
7. propose classification, split, or unresolved clarification
8. preserve project-owner authority for inferred/migrated architecture
```

The governing lifecycle obligation asks why a responsibility must exist, change, remain compatible, execute, or be retired.

Important frozen boundaries:

- Product-specific tests may be `PRODUCT`; reusable test SDK/framework/harness infrastructure may be `DEVELOPMENT_TOOLING`.
- Development/intermediate build support is normally `DEVELOPMENT_TOOLING`; authoritative release-unit build/assembly/signing/packaging is normally `DELIVERY`.
- `DELIVERY` ends at the semantic **delivery handoff** where the selected release reaches/is accepted by the destination and ordinary operation begins.
- Ongoing health/recovery/reconciliation/maintenance after handoff is `OPERATIONS`.
- When independently governable lifecycle responsibilities are mixed, split/redesign is preferred over choosing the majority of files, jobs, steps, runtime duration, or confidence score.
- If material ownership remains unresolved, fail closed rather than inventing a classification.

Normative rationale is recorded in `decisions/ADR-0007-primary-lifecycle-boundary-determination.md`.

## 5. Responsibility Map v2 semantic axes

These axes are deliberately independent:

```text
classification
    = primary lifecycle ownership

roles
    = coarse responsibility characteristics

relationships
    = project-owned typed directed semantic edges

VPMS Verification Purpose
    = what a Verification Case protects/verifies
```

### 5.1 Canonical component roles

```text
IMPLEMENTATION
VERIFICATION
AUTOMATION
CONFIGURATION
DOCUMENTATION
GOVERNANCE
```

Roles are optional, multi-valued, and non-classifying. Composite role proliferation such as `VERIFICATION_AUTOMATION` or `BUILD_RELEASE_AUTOMATION` is prohibited.

### 5.2 Canonical project-declared relationship types

```text
IMPORTS
LINKS
LOADS
INVOKES
READS
GENERATES
BUILDS
PACKAGES
PUBLISHES
DEPLOYS
VERIFIES
MANAGES
DOCUMENTS
SPECIFIES
GOVERNS
```

Direction is always:

```text
source --TYPE--> target
```

Observed evidence, project-owned relationship declaration, and allow/deny policy remain separate data. Evidence `TESTS` may support a `VERIFIES` proposal but does not silently create it.

### 5.3 Associated artifacts

An associated artifact is a project-owned non-component support surface subordinate to exactly one classified anchor component.

It MUST have:

- stable map identity;
- explicit selectors and purpose;
- exactly one anchor component;
- non-executable architectural role;
- no independently governable primary lifecycle;
- no independent release/compatibility lifecycle;
- at least one typed relationship to its anchor.

It has no classification or component roles and does not inherit its anchor's classification.

Promotion/re-evaluation as a component is required if independent executable, lifecycle, release, compatibility, Delivery, Operations, or cross-lifecycle authority responsibility emerges. Independently governed non-executable/non-owning lifecycle-independent contract semantics require `NEUTRAL_CONTRACT` evaluation.

Component IDs and associated-artifact IDs share one map-wide endpoint namespace.

Normative rationale is recorded in `decisions/ADR-0008-responsibility-roles-relationships-associated-artifacts.md` and `spec/PTSIP-RESPONSIBILITY-MAP.md`.

## 6. Responsibility Map modes

Tool `0.3.6` supports three canonical declaration modes.

### Explicit

The repository directly declares the complete canonical components, associated artifacts, and relationships.

### Template

The repository explicitly selects one supported template by stable ID and version/revision. Template selection MUST NOT be inferred from path, framework, language, package manager, or discovery confidence.

### Hybrid

The repository explicitly selects a version/revision-bound template and supplies ID-addressed project-owned overrides/extensions/removals.

Deterministic precedence is:

```text
explicit project override
    > selected template declaration
    > template default
```

Ambiguous/conflicting overrides fail closed.

## 7. WU-03 canonical activation state

WU-03 is complete at the implementation-contract level.

The canonical profile/schema/runtime now provides:

- five canonical classifications with no `TOOLCHAIN` alias;
- `responsibility_map.mode = explicit | template | hybrid`;
- closed multi-valued component roles;
- typed directed relationships;
- associated artifacts with anchor semantics;
- map-wide endpoint identity;
- lifecycle-neutral policy keys;
- explicit semantic validation beyond JSON Schema reference capability;
- fail-closed handling of unmaterialized template/hybrid maps for operations needing concrete component endpoints.

Canonical policy keys are:

```text
product_to_nonproduct_runtime_dependency: deny
nonproduct_in_product_package: deny
independent_build_resolution: required
shared_executable_cross_lifecycle: deny   # optional
neutral_contract_sharing: allow|deny      # optional
```

A separate canonical `lifecycle_owner` field is no longer persisted. Current authority/adoption input may temporarily carry `lifecycle_owner` as a compatibility fact, but after validation canonical profile ownership is represented only by `classification`.

The root PTSIP repository structurally self-adopts Responsibility Map v2:

- Tool runtime/library responsibility remains `PRODUCT`;
- repository verification/CI/maintenance use `DEVELOPMENT_TOOLING`;
- release/package delivery responsibility uses `DELIVERY`;
- canonical contracts remain `NEUTRAL_CONTRACT` where independent contract semantics hold;
- subordinate specification governance/adoption/agent support is represented through associated-artifact semantics where separate component ownership is unnecessary.

## 8. Template catalog — WU-04

WU-04 is the next work unit.

The initial catalog remains intentionally small. It MUST include at least:

1. Python package/library;
2. Python CLI/application;
3. mixed-lifecycle repository with Product plus development/release responsibilities.

Each template MUST have:

- stable template ID;
- immutable/versioned template revision;
- deterministic materialization;
- explicit component/relationship IDs;
- validation tests;
- no mandatory repository layout beyond declared template selectors;
- no auto-selection from discovery evidence.

Template-backed and hybrid maps MUST be materializable into the same canonical semantic model as explicit maps. If materialization cannot preserve confirmed project intent, it must fail rather than drop facts.

## 9. Evidence-driven candidate discovery

Candidate discovery must use evidence closer to actual execution/distribution/lifecycle behavior, including where available:

- invocation/entry-point/task evidence;
- package/build/project manifests;
- dependency/import/link/load/invocation edges;
- packaging/content evidence;
- workflow/build/test/release evidence;
- publication/promotion/deployment evidence;
- ongoing operations/maintenance/recovery evidence;
- explicit repository-owned declarations.

Path/name heuristics may remain low-confidence evidence but MUST NOT dominate stronger evidence or become architecture authority.

Prohibited shortcuts include:

```text
"tests/ exists" -> DEVELOPMENT_TOOLING
"src/ exists" -> PRODUCT
"GitHub Actions exists" -> DELIVERY
"Terraform exists" -> OPERATIONS
"pyproject.toml exists" -> select Python template
```

Discovery produces candidates + evidence + provenance. It may propose lifecycle ownership, role, relationship, associated artifact, and split candidates, but project-owned declaration remains authoritative.

## 10. Assisted Tool 0.3.5 migration

Migration is opt-in, preview-first, evidence-backed, and loss-preserving.

Blind mapping is prohibited:

```text
TOOLCHAIN -> DEVELOPMENT_TOOLING   # forbidden as a general migration rule
```

Expected candidate space:

| Tool 0.3.5 | Tool 0.3.6 candidate space | Rule |
| --- | --- | --- |
| `PRODUCT` | primarily `PRODUCT`; split/reclassification possible | never unconditional |
| `TOOLCHAIN` | `PRODUCT`, `DEVELOPMENT_TOOLING`, `DELIVERY`, `OPERATIONS`, split, unresolved | mandatory re-evaluation |
| `NEUTRAL_CONTRACT` | primarily `NEUTRAL_CONTRACT`; re-evaluate independence | never unconditional |

The migration analyzer must be able to propose:

- unchanged component;
- reclassification;
- component split;
- role changes;
- typed relationships;
- associated-artifact representation;
- unresolved clarification.

A legacy component containing `tools/**`, `tests/**`, workflows, deployment, and operations material may therefore split into several lifecycle-owned components rather than receive one renamed classification.

## 11. Migration preview and safe apply

Before any write, the migration workflow SHOULD show:

- source profile/version;
- source repository revision;
- evidence and provenance;
- proposed lifecycle classification(s);
- component-boundary effects;
- role/relationship/associated-artifact proposals;
- confidence/ambiguity;
- semantic diff;
- textual diff;
- unresolved facts.

The user/project owner confirms or edits architecture intent.

Safe apply MUST:

- re-check repository/profile freshness;
- preserve confirmed facts losslessly;
- refuse concurrent/stale writes;
- refuse target representations that cannot preserve confirmed semantics;
- never silently replace project-owned architecture authority.

Migration outputs may be:

- template-backed/hybrid declaration; or
- fully materialized canonical explicit map.

## 12. VPMS Specification visibility and boundary

Tool `0.3.6` makes VPMS visible in the normative Specification while keeping subsystem boundaries intact.

PTSIP asks:

```text
Who primarily owns this project responsibility across its lifecycle?
```

VPMS asks:

```text
Why does this verification exist / what does it protect?
```

Current VPMS Verification Purpose remains exactly:

```text
PRODUCT
TOOLCHAIN
```

VPMS `TOOLCHAIN` is VPMS vocabulary, not a Tool `0.3.6` PTSIP lifecycle classification. It MUST NOT be renamed merely as a side effect of the PTSIP ontology change.

PTSIP core MUST NOT acquire a VPMS runtime dependency. VPMS may consume stable/materialized PTSIP metadata through a narrow read-only boundary. VPMS PASS does not imply PTSIP CONFORMANT, and PTSIP CONFORMANT does not imply functional verification PASS.

## 13. Specification binding contract

For Tool `X.Y.Z`, release preparation requires:

```text
Tool X.Y.Z
    -> Specification X.Y.Z-draft
    -> immutable SPEC_REVISION
```

For Tool `0.3.6`, current development binding is:

```text
Tool 0.3.6
Specification 0.3.6-draft
SPEC_REVISION 12e2ccd15634ecb3d0a4195b0f61ac3f620e7540
```

Release preparation must fail unless:

1. package Tool version is correct;
2. constants bind `<Tool version>-draft`;
3. `SPEC_REVISION` is a full immutable commit SHA;
4. the revision exists and is an ancestor of release source;
5. all required canonical Specification files exist at that revision, including `spec/PTSIP-RESPONSIBILITY-MAP.md`;
6. root `ptsip.yaml` binds the same source/version/revision;
7. embedded schema/registry assets match canonical copies where required;
8. `releasenote/spec-<SPEC_VERSION>.md` exists and is non-empty;
9. exact release-candidate SHA has passed the required self-hosted verification.

This is a release gate, not a documentation reminder.

## 14. `AGENTS.md`, `MEMORY.md`, and `STATUS.md`

These are repository-operational documents, not replacements for the normative Specification.

- `AGENTS.md` defines coding-agent behavior.
- `MEMORY.md` records durable active repository/release/architecture context.
- `STATUS.md` distinguishes published Tool state from active development state.
- agents must still read root `ptsip.yaml`, Tool constants, applicable Specification, and the active plan.

All three must distinguish published Tool `0.3.5` historical semantics from development Tool `0.3.6` canonical semantics.

## 15. Self-hosted workflow resource policy

GitHub-hosted Actions usage is constrained.

Approved Windows self-hosted runner:

```text
DESKTOP-5HCCQIR
```

Self-hosted execution is the default for:

- repository regression/verification;
- release-candidate exact-SHA verification;
- release preparation;
- distribution build and verification.

`tooling-test.yml` is manual self-hosted verification and MUST NOT gain automatic push/PR/tag/schedule/release triggers merely for convenience.

Before dispatching `tooling-test.yml` or `release.yml`, the user must be told the self-hosted runner will be used and must explicitly confirm that the host and PowerShell environment are ready.

For a release candidate:

```text
final main SHA
    -> tooling-test.yml(host_ready=true, release_candidate=true, source_sha=<exact SHA>)
    -> self-hosted/release-verification on that exact SHA
    -> release.yml(host_ready=true, source_sha=<same SHA>)
    -> draft release targets same SHA without repository mutation
```

`tooling-release.yml` performs distribution build/verification on the approved self-hosted Windows runner.

### Only current GitHub-hosted exception

The narrow GNU/Linux PyPI Trusted Publishing job may remain GitHub-hosted because `pypa/gh-action-pypi-publish` is Docker-based and cannot execute on the approved Windows self-hosted runner.

That job may only:

```text
download already verified distributions
    -> PyPI Trusted Publishing
```

It MUST NOT absorb repository tests, compilation, package building, release preparation, or other avoidable compute.

No automatic GitHub-hosted verification matrix is introduced for convenience.

## 16. Non-goals

Tool `0.3.6` does not aim to:

- retain `TOOLCHAIN` as a canonical alias;
- silently reinterpret Tool `0.3.5` profiles as Tool `0.3.6` profiles;
- classify by path/framework/language/test/workflow technology;
- force all tests into one lifecycle;
- force one repository layout or development style;
- automatically select a template from discovery evidence;
- make supported templates mandatory;
- silently overwrite project-owned responsibility facts;
- create a lifecycle classification for every internal role;
- use associated artifacts to evade classification;
- collapse PTSIP classification, role, relationship, and VPMS purpose;
- treat `AGENTS.md`/`MEMORY.md` as normative Specification;
- automatically dispatch or power on the self-hosted runner.

## 19. Development and release success criteria

Tool `0.3.6` is development-complete when:

- five primary lifecycle classifications are implemented consistently;
- Responsibility Map v2 explicit/template/hybrid modes are usable;
- role/relationship/associated-artifact semantics are preserved losslessly;
- candidate discovery uses structural/runtime evidence rather than path-only authority;
- valid Tool `0.3.5` profiles are readable as legacy migration inputs;
- migration can propose reclassification/split/relationship/artifact changes with evidence;
- user/project-owner confirmation remains architecture authority;
- safe migration apply is stale/concurrency protected;
- VPMS remains orthogonal and functional;
- PTSIP repository dogfood succeeds;
- canonical and embedded contracts are coherent;
- full self-hosted regression/package verification succeeds.

Tool `0.3.6` is release-ready only after the exact final `main` SHA also satisfies the Specification release contract and self-hosted exact-SHA release verification.

## 20. Future version boundary

Do not create a separate Tool `0.4.0` plan merely because Tool `0.3.6` contains a breaking schema migration. The `0.x` line remains experimental and Tool `0.3.6` deliberately provides an assisted migration path from published Tool `0.3.5`.

A later `0.4.0` should be opened only if an independently consequential scope emerges beyond the work consolidated here. A `1.0.0` release should wait until the ownership ontology, Responsibility Map schema, migration behavior, conformance evidence, and real-project adoption are materially stable.
