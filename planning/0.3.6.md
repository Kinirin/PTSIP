## 2. Sub-document creation and entry discipline

Future sub-stage documents MUST NOT be pre-created.

Required process:

```text
current stage ACTIVE
    -> complete its declared implementation gate
    -> freshly read development branch HEAD
    -> record predecessor completion
    -> create next stage sub-document with exact entry SHA
    -> mark only that implementation stage ACTIVE
    -> begin only that stage
```

Rules:

1. only one WU-04 implementation sub-stage is ACTIVE at a time;
2. later stages remain `LOCKED` until the predecessor implementation gate is complete;
3. a future sub-document is created only at actual stage entry;
4. every sub-document records predecessor and exact entry baseline SHA;
5. implementation must not jump ahead because a later integration is convenient;
6. sequencing changes are recorded here before entering an affected stage.

WU-04A/B predate this sub-document rule and remain completed history without retroactive stage documents.

### WU-04E/WU-04F combined verification tranche

For the maintainer-directed 2026-08-19 E/F session, implementation ordering remains strict but **execution verification is intentionally shared**:

```text
WU-04E implementation gate
    -> mark E implementation complete
    -> fresh branch-HEAD read
    -> enter WU-04F
    -> complete F implementation
    -> one exact-SHA self-hosted tooling-test run validates E + F together
```

This is a verification-cadence exception, not an architecture-order exception. WU-04F did not begin until the WU-04E implementation gate was satisfied. WU-04E must not be described as exact-SHA verified until the shared E/F run succeeds; if that run exposes an E regression, WU-04E is reopened before proceeding beyond F. WU-04G remains locked until the combined E/F verification result is reviewed and F's completion gate is satisfied.

## 3. Canonical architecture boundaries

Canonical PTSIP lifecycle classifications remain exactly:

```text
PRODUCT
DEVELOPMENT_TOOLING
DELIVERY
OPERATIONS
NEUTRAL_CONTRACT
```

`TOOLCHAIN` is Tool `0.3.5` legacy migration input only.

These axes remain independent:

```text
classification
    = primary lifecycle ownership

roles
    = coarse responsibility characteristics

relationships
    = project-owned typed directed semantics

source_mode / derived origin
    = declaration authority provenance

VPMS Verification Purpose
    = what verification protects/verifies
```

Canonical Responsibility Map source modes are:

```text
explicit
template
hybrid
```

The accepted declaration/materialization authority boundary is recorded in `decisions/ADR-0009-responsibility-map-declaration-authority.md` and normatively frozen by `PTSIP-RMAP-013` through `PTSIP-RMAP-016`.

Materialization is deterministic and non-authoritative. Template selection is explicit and revision-bound. Hybrid precedence is stable-ID whole-entity replacement/extension/removal over the selected immutable template declaration.

## 4. Canonical Effective Responsibility Map

All declaration modes resolve to one downstream semantic model:

```text
explicit ----+
template ----+--> Canonical Effective Responsibility Map
hybrid ------+
                    |
                    +--> components
                    +--> associated_artifacts
                    +--> relationships
                    +--> component_dependency_policy
                    +--> policies
```

The original source declaration and exact template identity remain separately available. Materialization MUST NOT infer architecture, select templates from discovery evidence, rewrite lifecycle ownership, repair dangling relationships, or mutate source declarations merely to produce a valid map.

## 6. WU-04F boundary

WU-04F moves Enforced Conformance onto the runtime abstraction handed off by WU-04E:

```text
source ptsip.yaml
      |
      v

      |
      v
ValidationResult.resolved_profile
      |

      |
      +--> dependency-boundary evaluation
      +--> artifact/component identity evaluation
      +--> project component-dependency policy
      +--> source-language / ownership coverage
```

Conformance must not reload canonical architecture from raw source `components`, infer template semantics, or retain a `materialization-required` branch. Invalid profiles remain fail-closed. Clarification/adoption and VPMS integrations remain deferred to WU-04G and WU-04H.

## 7. Tool 0.3.5 migration boundary

Compatibility means assisted migration, not obsolete ontology preservation:

```text
Tool 0.3.5 profile
    -> legacy reader
    -> evidence/provenance collection
    -> lifecycle/role/relationship/split/artifact proposals
    -> project-owner confirmation
    -> canonical Tool 0.3.6 Responsibility Map
```

Blind `TOOLCHAIN -> DEVELOPMENT_TOOLING` translation is prohibited. Legacy `lifecycle_owner`, `consumers`, `analysis_inputs`, old boundary roots, and untyped dependency-policy edges remain migration evidence rather than automatic canonical mappings.

Candidate discovery and migration analysis produce evidence/proposals, not architecture authority.

## 11. Self-hosted verification and release resource policy

Self-hosted execution is capability-bound, not machine-name-bound. Eligible Windows build/test runners must satisfy:

```text
self-hosted
Windows
X64
PowerShell
Python 3.14 available through `py -3.14`
```

Repository regression, release preparation, and distribution build default to self-hosted execution. If no matching runner is online, GitHub Actions may remain queued until one becomes available; do not duplicate scheduler state with a `host_ready` input.

`tooling-test.yml` and `release.yml` are manual workflows with no custom SHA/host/release-candidate inputs. The selected ref's immutable execution SHA is derived from `github.sha` and verified after checkout.

The only current GitHub-hosted compute exception is the narrow GNU/Linux PyPI Trusted Publishing job. No WU-04 development stage automatically dispatches the self-hosted runner.
