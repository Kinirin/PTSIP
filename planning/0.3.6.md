## 2. Sub-document creation and entry discipline

Future sub-stage documents MUST NOT be pre-created merely to describe possible later work.

The required process is:

```text
current stage ACTIVE
    -> complete its declared gate
    -> freshly read development branch HEAD
    -> record predecessor completion
    -> create next stage sub-document
    -> mark next stage ACTIVE
    -> begin that stage only
```

Rules:

1. only one WU-04 sub-stage is ACTIVE at a time;
2. future stages remain `LOCKED` until their predecessor gate is satisfied;
3. a future sub-document is created only when that stage is actually entered;
4. a sub-document must record its entry baseline SHA and predecessor;
5. work must not jump ahead merely because a later implementation looks convenient;
6. if a new architecture decision changes later sequencing, update this master document before entering the affected stage;
7. WU-04A/B were implemented before this sub-document rule was adopted, so they are recorded here as completed history rather than retroactively creating artificial entry documents.

## 4. Responsibility Map declaration modes

Canonical source modes are:

```text
explicit
template
hybrid
```

`source_mode` describes **declaration source/authority structure**, not lifecycle ownership.

The accepted authority boundary is recorded in:

```text
decisions/ADR-0009-responsibility-map-declaration-authority.md
```

Summary:

```text
classification
    = lifecycle responsibility

source_mode / derived origin
    = declaration authority provenance

materializer
    = deterministic, non-authoritative resolution
```

Mode authority:

```text
explicit
    project owns complete declaration

template
    project owns exact template selection
    selected immutable template revision supplies adopted declaration content

hybrid
    project owns exact template selection plus stable-ID replace/add/remove decisions
    selected template supplies only unchanged declarations
```

Hybrid precedence is:

```text
project override / extension / removal
    > selected immutable template declaration
```

Tool `0.3.6` uses whole-entity stable-ID replacement rather than field-level hybrid inheritance.

Materialization MUST NOT infer architecture, auto-select templates, silently repair broken relationships, rewrite lifecycle ownership, or cascade-delete related entities merely to make an effective map valid.

## 5. Canonical Effective Responsibility Map

All declaration modes must resolve to one downstream semantic model:

```text
explicit ----+
template ----+--> Canonical Effective Responsibility Map
hybrid ------+
                    |
                    +--> components
                    +--> associated_artifacts
                    +--> relationships
                    +--> dependency policy
                    +--> project policies
```

Downstream evaluators should consume this effective view rather than implement separate architecture semantics for each source mode.

The original source declaration and template identity remain separately available for provenance, migration preview, review, and safe apply.

A deterministic `effective_map_digest` is planned for semantic-equivalence/reproducibility checks, but the digest never becomes architecture authority.

## 8. Tool 0.3.5 compatibility and migration boundary

Tool `0.3.5` canonical input vocabulary is historical:

```text
PRODUCT
TOOLCHAIN
NEUTRAL_CONTRACT
```

Tool `0.3.6` compatibility means:

```text
legacy reader
    -> evidence/provenance collection
    -> lifecycle/role/relationship/split/artifact proposal
    -> project-owner confirmation
    -> canonical 0.3.6 Responsibility Map
```

Blind mapping such as:

```text
TOOLCHAIN -> DEVELOPMENT_TOOLING
```

is prohibited.

A legacy `TOOLCHAIN` responsibility may resolve to Product, Development Tooling, Delivery, Operations, split, or unresolved clarification depending on governing lifecycle evidence.

Legacy `lifecycle_owner`, `consumers`, `analysis_inputs`, old boundary roots, and untyped dependency-policy edges remain migration evidence rather than automatic canonical fields/relationships.

## 9. Evidence and project authority boundary

Candidate discovery and migration analysis produce evidence and proposals, not architecture authority.

Prohibited shortcuts include:

```text
tests/ exists        -> DEVELOPMENT_TOOLING
github workflow      -> DELIVERY
Terraform exists     -> OPERATIONS
pyproject.toml exists -> auto-select Python template
```

Path, technology, manifest, or confidence may contribute evidence but cannot silently replace a project-owned responsibility declaration.

## 10. VPMS boundary

PTSIP asks:

```text
Which lifecycle owns this responsibility?
```

VPMS asks:

```text
Why does this verification exist / what does it protect?
```

VPMS Verification Purpose remains independently governed and currently uses:

```text
PRODUCT
TOOLCHAIN
```

VPMS `TOOLCHAIN` is not a PTSIP Tool `0.3.6` lifecycle classification.

PTSIP core MUST NOT depend on VPMS. VPMS may consume stable PTSIP metadata through a narrow read-only boundary only after PTSIP has resolved the effective map.
