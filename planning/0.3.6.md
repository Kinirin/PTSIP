# PTSIP Tool 0.3.6 — Lifecycle Ownership Expansion, Responsibility Map v2, Evidence-Driven Migration, and Specification Discipline

> **Status:** PLANNED  
> **Target Tool version:** `0.3.6`  
> **Published baseline:** Tool `0.3.5`  
> **Required Specification family before release:** `0.3.6-draft`  
> **Primary goal:** expand PTSIP classification into a primary-lifecycle-ownership model, generalize the repository-owned Responsibility Map without preserving obsolete classification semantics in the new canonical schema, provide evidence-driven assisted migration from Tool `0.3.5`, add typed responsibility relationships and associated-artifact representation, strengthen candidate discovery, make VPMS visible in the normative Specification, and make Specification binding a mandatory release contract.

## 1. Scope consolidation

Tool `0.3.6` absorbs the previously separate `0.4.0` candidate-discovery plan because implementation has not yet begun and the work is now directly coupled to Responsibility Map v2 and legacy migration.

The former `0.4.0` plan focused on reducing dependency on repository-name and path heuristics when discovering component candidates. That work is required before migrating the Tool `0.3.5` three-classification model because `TOOLCHAIN` can no longer be treated as a one-to-one rename.

Tool `0.3.6` therefore becomes the first release whose canonical Responsibility Map is based on **primary lifecycle ownership** rather than the original Product/Toolchain SDK split alone.

Candidate discovery, migration analysis, role inference, relationship inference, and component-split detection remain evidence-producing operations. They do **not** become project architecture authority.

## 2. Tool 0.3.5 compatibility contract

Tool `0.3.5` was published with these canonical architecture classifications:

- `PRODUCT`;
- `TOOLCHAIN`;
- `NEUTRAL_CONTRACT`.

Tool `0.3.6` MUST understand valid Tool `0.3.5` profiles as **legacy migration inputs**. Compatibility does not mean that the new canonical schema continues to accept the old ontology indefinitely.

The Tool `0.3.6` canonical classification set is:

- `PRODUCT`;
- `DEVELOPMENT_TOOLING`;
- `DELIVERY`;
- `OPERATIONS`;
- `NEUTRAL_CONTRACT`.

`TOOLCHAIN` MUST NOT be emitted as a canonical Tool `0.3.6` classification and MUST NOT be retained as an alias in the new canonical classification enum merely for compatibility.

The compatibility boundary is:

```text
Tool 0.3.5 profile
    PRODUCT | TOOLCHAIN | NEUTRAL_CONTRACT
        |
        v
legacy profile reader
        |
        v
repository evidence + existing declaration analysis
        |
        v
migration proposal
        |
        v
maintainer/project-owner confirmation
        |
        v
Tool 0.3.6 canonical Responsibility Map
    PRODUCT | DEVELOPMENT_TOOLING | DELIVERY | OPERATIONS | NEUTRAL_CONTRACT
```

A Tool `0.3.5` profile is therefore supported for inspection and migration, not silently reinterpreted as if it already had Tool `0.3.6` semantics.

## 3. Primary lifecycle ownership classification

Tool `0.3.6` defines `classification` as the **primary lifecycle ownership of a project-owned architectural responsibility**.

Classification MUST NOT be derived solely from file type, programming language, framework, executable status, compilation behavior, directory name, workflow location, or whether an artifact is a test.

The same artifact kind MAY legitimately occur under different classifications when lifecycle ownership differs.

### 3.1 `PRODUCT`

`PRODUCT` represents responsibility owned directly by the Product lifecycle, including Product runtime, user-facing behavior, Product distribution content, runtime SDK responsibility, and Product-specific quality or verification responsibility.

Representative examples include:

- Product-owned tests;
- FastAPI applications;
- Cloudflare Worker applications;
- desktop applications;
- runtime SDKs;
- Product-specific validation;
- Product package contents.

A test is not automatically Development Tooling. Tests whose existence, change responsibility, and compatibility expectations are owned by a Product MAY be classified as `PRODUCT`.

### 3.2 `DEVELOPMENT_TOOLING`

`DEVELOPMENT_TOOLING` represents responsibility owned by the development lifecycle and used to create, transform, inspect, validate, migrate, or otherwise support development work.

Representative examples include:

- reusable tests or verification infrastructure;
- test SDKs/frameworks;
- generators;
- migration tooling;
- linting;
- static analysis;
- developer CLI tooling;
- build helpers;
- repository transformation utilities;
- development-environment tooling.

This classification carries the core development-tool responsibility previously represented by much of Tool `0.3.5` `TOOLCHAIN`, but it is not a universal replacement for every old `TOOLCHAIN` component.

### 3.3 `DELIVERY`

`DELIVERY` represents responsibility for carrying a release target or Product from build/release preparation through publication, promotion, distribution, or deployment to its destination environment.

Representative examples include:

- release workflows;
- package publication;
- container image build/publication;
- artifact signing;
- deployment automation;
- deployment manifests/configuration;
- release promotion.

The guiding distinction is:

```text
PRODUCT
    -> what Product responsibility or distributable exists

DELIVERY
    -> how that release target is carried to a publication or deployment destination
```

### 3.4 `OPERATIONS`

`OPERATIONS` represents responsibility owned by the post-deployment operational lifecycle: keeping a deployed system healthy, recoverable, maintained, and operational over time.

Representative examples include:

- production provisioning where the responsibility is ongoing operational state rather than one-time delivery;
- runtime infrastructure management;
- operational automation;
- backup/recovery;
- production maintenance;
- incident tooling;
- production health management.

`DELIVERY` and `OPERATIONS` are separated by primary lifecycle purpose, not by technology. A deployment or infrastructure tool MAY require explicit project-owner resolution when it performs both delivery-time and ongoing operational responsibilities.

### 3.5 `NEUTRAL_CONTRACT`

`NEUTRAL_CONTRACT` preserves the independent-contract concept: deliberately non-executable, non-owning contract responsibility with lifecycle independence from Product, Development Tooling, Delivery, and Operations ownership.

Its defining properties remain:

```text
non-executable
non-owning
independent lifecycle
```

Schemas, IDLs, protocol definitions, registries, test vectors, and immutable contract manifests MAY qualify when these semantics are actually present. File format or documentation form alone does not create neutrality.

### 3.6 Artifact kind does not determine classification

Tool `0.3.6` MUST explicitly permit cases such as:

```text
Product-specific tests
    -> PRODUCT

shared test SDK / reusable verification infrastructure
    -> DEVELOPMENT_TOOLING

Product runtime source
    -> PRODUCT

release/publish workflow
    -> DELIVERY

post-deployment maintenance automation
    -> OPERATIONS
```

PTSIP MUST NOT impose one mandatory project directory layout or force users to adopt a particular testing/development style merely to satisfy classification.

Technology names are evidence, not authority. FastAPI, Cloudflare Workers, GitHub Actions, Docker, Terraform, PowerShell, Python, Markdown, or YAML do not have universal PTSIP classifications by themselves.

## 4. Classification, role, relationship, and VPMS are separate axes

Responsibility Map v2 MUST avoid encoding every architectural distinction into classification.

The conceptual separation is:

```text
classification
    = primary lifecycle ownership

role
    = responsibility performed inside that lifecycle

relationship
    = typed semantic relationship to another responsibility or artifact

VPMS verification purpose
    = what a Verification Case protects/verifies
```

A `PRODUCT` component MAY have a verification role. A `DEVELOPMENT_TOOLING` component MAY also have a verification role. The role does not determine lifecycle ownership.

Likewise, multiple components in the same lifecycle classification MAY perform materially different responsibilities and MUST be able to preserve those distinctions without creating more lifecycle classifications.

Exact role vocabulary MUST remain small and schema-governed. Tool `0.3.6` MUST NOT create combinatorial role names merely to encode multiple relationships in one field.

## 5. Typed relationships and associated artifacts

Responsibility Map v2 MUST provide a structured way to preserve component-to-component responsibility semantics that cannot currently be represented losslessly by untyped `from`/`to` dependency rules.

The design SHOULD reuse existing PTSIP relationship vocabulary where semantics already exist, including concepts such as testing, generation, packaging, and publication, before introducing overlapping names.

Additional relationship concepts required by real project feedback MAY include governance/documentation semantics such as:

- `DOCUMENTS`;
- `SPECIFIES`;
- `GOVERNS`.

Build, verification, production, publication, or deployment relationship names MUST be normalized against existing Specification vocabulary before their exact canonical IDs are frozen.

Responsibility Map v2 MUST also be able to represent project-owned associated documentation/authority/support artifacts that relate to a component but do not need to become separate architecture components merely to express that relationship.

Associated-artifact representation MUST NOT become a classification escape hatch. At minimum:

- an associated artifact MUST NOT be used to hide an independently owned architectural responsibility that should be a component;
- executable responsibility requires component evaluation;
- independent release/compatibility/lifecycle ownership requires component evaluation;
- an independently owned cross-lifecycle contract requires `NEUTRAL_CONTRACT` evaluation;
- associated-artifact or relationship declarations MUST NOT weaken mandatory dependency, packaging, lifecycle, or conformance rules.

## 6. Responsibility Map modes

Tool `0.3.6` must support three project-owned modes.

### Explicit

The repository declares the complete Tool `0.3.6` Responsibility Map directly. Existing Tool `0.3.5` explicit profiles remain readable as migration inputs but are not automatically canonical Tool `0.3.6` profiles.

### Template

The repository explicitly selects one supported, versioned Responsibility Map template. A template is never selected by directory-name heuristics or by candidate-discovery evidence alone.

### Hybrid

The repository selects a supported template and supplies project-owned overrides/extensions. Explicit repository declarations take precedence over template defaults inside the schema-defined override boundary. Ambiguous or conflicting overrides fail closed rather than being guessed.

## 7. Initial supported templates

The first catalog should remain small and useful. Tool `0.3.6` should include at least these common responsibility shapes, with exact stable IDs frozen during implementation:

1. Python package/library;
2. Python CLI/application;
3. mixed-lifecycle repository with Product and development/release responsibilities.

Templates standardize useful starting declarations. They do **not** make directory names normative, restrict user testing style, or prevent a repository from using a completely custom explicit map.

Template identities must be versioned or revision-bound so a later PTSIP release cannot silently change the meaning of a previously selected template.

## 8. Evidence-driven candidate discovery

Tool `0.3.6` must broaden candidate discovery so it can use repository evidence closer to actual execution, distribution, dependency, delivery, and operations behavior.

The discovery engine should consider at least the following evidence classes where available:

- **invocation evidence** — commands, entry points, workflow invocations, executable scripts, launch configuration, task definitions, and other evidence that a repository artifact is actually invoked;
- **manifest evidence** — package/build/project manifests and declared package or application metadata;
- **dependency evidence** — imports, package dependencies, internal references, build dependencies, runtime/development dependency edges, and other dependency-graph evidence;
- **packaging evidence** — files or modules included in or excluded from built/distributed artifacts;
- **workflow/build evidence** — CI, build, release, test, maintenance, publication, and deployment automation that demonstrates lifecycle responsibility;
- **delivery evidence** — release targets, package/container publication, promotion, deployment configuration, and destination-facing automation;
- **operations evidence** — recurring production management, backup/recovery, health, reconciliation, incident, and maintenance behavior;
- **explicit project declarations** — current `ptsip.yaml`, template selection, overrides, or other authoritative repository-owned metadata.

Path and name heuristics may remain as low-confidence discovery evidence where useful, but they must not dominate stronger evidence and must not become responsibility authority.

Candidate discovery produces **evidence**, not final lifecycle ownership decisions.

```text
repository evidence
    -> candidate discovery
    -> candidate + evidence set
    -> lifecycle/role/relationship/split proposal
    -> project declaration or clarification
```

The discovery layer must preserve provenance so an agent or maintainer can see *why* each proposal was produced.

## 9. Candidate discovery and project authority boundary

Improved discovery is intentionally separated from Responsibility Map authority.

The following are prohibited:

```text
"pyproject.toml exists"
    -> automatically choose Python package template

"tests/ exists"
    -> automatically classify as DEVELOPMENT_TOOLING

"src/ exists"
    -> automatically classify as PRODUCT

"GitHub Actions workflow exists"
    -> automatically classify as DELIVERY

"Terraform exists"
    -> automatically classify as OPERATIONS
```

Instead, multiple evidence classes may support a proposal and confidence assessment. A coding agent may present the proposal and supporting evidence, but the project owner/maintainer retains architecture authority when evidence does not reproduce an already explicit project-owned fact.

High-confidence inference is still a proposal when it changes lifecycle ownership or component boundaries.

## 10. Tool 0.3.5 assisted migration

Migration from Tool `0.3.5` is opt-in, preview-first, and evidence-driven.

The Tool MUST NOT implement a blind enum translation such as:

```text
TOOLCHAIN -> DEVELOPMENT_TOOLING
```

because old `TOOLCHAIN` responsibility may actually map to Development Tooling, Delivery, Operations, or a Product-owned responsibility that was previously forced into an overly broad classification.

Initial migration expectations are:

| Tool 0.3.5 classification | Tool 0.3.6 candidate space | Migration expectation |
| --- | --- | --- |
| `PRODUCT` | primarily `PRODUCT`, with split/reclassification proposals when evidence exposes mixed lifecycle ownership | high-probability carry-forward, never unconditional |
| `TOOLCHAIN` | `DEVELOPMENT_TOOLING`, `DELIVERY`, `OPERATIONS`, and in some cases `PRODUCT` | mandatory lifecycle re-evaluation |
| `NEUTRAL_CONTRACT` | primarily `NEUTRAL_CONTRACT`, with re-evaluation when independence/non-ownership evidence is absent | high-probability carry-forward, never unconditional |

The migration analyzer MUST be able to propose more than a classification rename. It SHOULD be able to identify:

- unchanged component candidates;
- classification-change candidates;
- component-split candidates;
- associated-artifact candidates;
- typed relationship candidates;
- unresolved/ambiguous candidates.

Example:

```text
old TOOLCHAIN component
    tools/**
    tests/**
    .github/workflows/**
    deploy/**
        |
        v
migration evidence
        |
        +-> reusable verification/generator responsibility
        |       -> DEVELOPMENT_TOOLING
        |
        +-> release/publish/deploy responsibility
        |       -> DELIVERY
        |
        +-> post-deployment maintenance responsibility
                -> OPERATIONS
```

The coding agent/CLI SHOULD present the proposal, supporting evidence, confidence/ambiguity, component-boundary effects, and semantic/textual diff. The user should be responsible for architecture confirmation rather than manually performing repository-wide evidence collection.

Migration MUST NOT silently rewrite repository-owned architecture intent.

## 11. Migration outputs and precedence

Two migration outputs should be supported:

- **template-backed migration** — keep a selected template identity and store only required project overrides/extensions;
- **materialized migration** — expand the selected template into a complete canonical Tool `0.3.6` project-owned map so runtime template resolution is no longer required.

Migration must preserve project-specific facts such as `purpose`, selectors, lifecycle ownership evidence, shipping/runtime facts, consumers, analysis inputs, release ownership, compatibility ownership, associated artifacts, and typed relationships unless the maintainer explicitly changes them.

If the selected template/override model cannot represent the current architecture intent losslessly, migration must stop and report the unresolved facts instead of dropping them.

Responsibility resolution must be deterministic:

```text
explicit project override
    >
selected template declaration
    >
template default
```

Candidate-discovery evidence can propose changes but cannot override explicit project-owned facts during migration without explicit project-owner confirmation.

## 12. VPMS becomes Specification-visible

Tool `0.3.5` shipped VPMS while remaining bound to `0.3.4-draft`. Tool `0.3.6` must close the resulting agent-policy gap by creating a new `0.3.6-draft` Specification that normatively records at least:

- VPMS — Verification Purpose Management System;
- PTSIP lifecycle classification and VPMS verification purpose as separate axes;
- Verification Case as the purpose-bound execution unit;
- Formula, Variables, Policy, Target, and Runner separation;
- Formula reuse without lifecycle-classification collapse;
- Product-owned tests and reusable Development Tooling verification as both valid patterns;
- PTSIP core MUST NOT depend on VPMS;
- VPMS may consume stable PTSIP metadata through a narrow read-only boundary;
- VPMS PASS does not imply PTSIP CONFORMANT, and PTSIP CONFORMANT does not imply functional verification PASS;
- Responsibility Map v2 lifecycle ownership semantics;
- typed role/relationship and associated-artifact semantics;
- Tool `0.3.5` legacy-reader and assisted-migration semantics;
- candidate discovery as evidence acquisition rather than responsibility authority;
- evidence provenance and no-path-only-inference requirements.

The exact VPMS purpose vocabulary is a separate axis and MUST NOT be changed merely as an accidental side effect of replacing the Tool `0.3.5` lifecycle classification name `TOOLCHAIN`.

## 13. Mandatory Specification release contract

Starting with Tool `0.3.6`, release preparation must fail unless all of the following are true:

1. `pyproject.toml` declares the requested Tool version;
2. `src/ptsip/constants.py` binds `SPEC_VERSION` to `<Tool version>-draft`;
3. `SPEC_REVISION` is a full immutable Git commit SHA;
4. the Specification revision exists and is an ancestor of the release source;
5. canonical Specification files exist at that revision;
6. root `ptsip.yaml` binds the same Specification version, source, and revision;
7. `releasenote/spec-<SPEC_VERSION>.md` exists and is non-empty;
8. the exact release-candidate source SHA has passed the required self-hosted verification.

This is a release gate, not a documentation reminder. The pipeline must reject a release that omits the Specification work.

## 14. `AGENTS.md` and `MEMORY.md`

Root `AGENTS.md` and `MEMORY.md` are repository-operational inputs for coding agents.

- `AGENTS.md` defines required working behavior.
- `MEMORY.md` records durable current repository/release/architecture context.
- Neither replaces the normative Specification.
- Agents must read both before planning or modifying the repository.
- Agents must still read `ptsip.yaml` and the bound Specification.
- Agents must treat lifecycle, role, relationship, split, and migration proposals as evidence-backed proposals rather than permission to silently rewrite project-owned responsibility facts.

## 15. Self-hosted verification policy

GitHub-hosted Actions usage is constrained. Full repository testing and release-candidate verification use the single `.github/workflows/tooling-test.yml` workflow in manual self-hosted mode.

Expected runner identity:

```text
DESKTOP-5HCCQIR
```

The self-hosted test workflow must:

- use a self-hosted Windows runner;
- verify `RUNNER_NAME == DESKTOP-5HCCQIR` before repository work;
- require explicit host-ready acknowledgement;
- never run automatically on push, pull request, tag, schedule, or release;
- run the complete pytest/CLI/build/wheel smoke boundary when manually dispatched;
- support release-candidate verification for one exact SHA.

Before any coding agent or maintainer automation dispatches the self-hosted workflow, the user must be told that the runner will be used and must explicitly confirm that the host and PowerShell environment are ready.

The release-preparation workflow may remain GitHub-hosted for lightweight release orchestration, and the PyPI publication workflow may remain GitHub-hosted for Trusted Publishing. They must not duplicate the expensive full test suite once the self-hosted gate is active.

## 16. Non-goals

Tool `0.3.6` does not aim to:

- preserve `TOOLCHAIN` as a canonical alias in the new schema;
- silently reinterpret Tool `0.3.5` profiles as Tool `0.3.6` profiles;
- automatically decide lifecycle ownership from a filename, directory, programming language, framework, test status, or workflow platform;
- force all tests into `PRODUCT` or `DEVELOPMENT_TOOLING`;
- force users to adopt a specific repository layout or testing/development style;
- make a supported template mandatory;
- silently overwrite project-owned responsibility facts;
- make template component IDs mandatory for custom repositories;
- classify responsibility directly from candidate-discovery confidence;
- automatically select a template from manifest, dependency, packaging, invocation, deployment, operations, or path evidence;
- create a new lifecycle classification for every internal role;
- use associated artifacts to bypass classification requirements;
- collapse PTSIP lifecycle classification, responsibility role, typed relationship, and VPMS verification purpose into one axis;
- turn `MEMORY.md` or `AGENTS.md` into normative Specification documents;
- automatically power on or dispatch the self-hosted runner.

Recommended dependency flow:

```text
WU-00
  |

  |                                                  |
  +--> WU-05 ------------------> WU-06 -------------+--> WU-07 --> WU-08 --> WU-09
                                                     |

```

`WU-01` and `WU-05` may proceed in parallel after the initial Specification baseline, but migration implementation MUST wait until the lifecycle ontology, schema direction, and evidence model are stable enough to avoid encoding obsolete three-classification assumptions.

Typed relationship/associated-artifact design MUST be settled before Responsibility Map v2 schema freeze so the new schema does not require an immediate follow-up migration merely to represent responsibilities already identified by user feedback.

Tool `0.3.6` is therefore the compatibility-and-ontology transition release: it understands the published Tool `0.3.5` model, assists users in migrating it, but establishes the new five-classification primary-lifecycle model as the canonical forward architecture.
