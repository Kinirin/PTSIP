# PTSIP Tool 0.3.6.1 — Evidence-Driven Migration Continuation Plan

> **Status:** PLANNED / NOT ENTERED  
> **Target Tool version:** `0.3.6.1`  
> **Predecessor release:** Tool `0.3.6`  
> **Planning split baseline:** `3529a32c862e1d43a91f732ced36358b4e13e1d9`  
> **Canonical architecture basis:** Tool `0.3.6` Primary Lifecycle Ownership + Responsibility Map v2  
> **Required Specification family before release:** `0.3.6.1-draft`

## 1. Purpose

Tool `0.3.6.1` continues the evidence-driven migration work that was originally part of the Tool `0.3.6` roadmap.

The split exists to let Tool `0.3.6` release its already-established lifecycle-ownership foundation without treating the much larger migration system as unfinished Tool `0.3.6` work.

Tool `0.3.6.1` does not define a new lifecycle ontology. It consumes the canonical model introduced by Tool `0.3.6`:

```text
PRODUCT
DEVELOPMENT_TOOLING
DELIVERY
OPERATIONS
NEUTRAL_CONTRACT
```

`TOOLCHAIN` remains Tool `0.3.5` legacy input only and is never a canonical Tool `0.3.6.1` classification.

## 2. Migration pipeline

```text
repository facts
    -> candidate discovery
    -> normalized evidence + provenance
    -> Tool 0.3.5 legacy read model
    -> migration analysis
    -> target proposals
    -> project-owner preview / confirmation
    -> safe migration apply
```

The authority boundary remains:

```text
Evidence != Authority
Inference != Authority
Proposal != Authority

accepted project-owned architecture decision
    -> exact authorized write delta
```

No confidence score, repository convention, path heuristic, or materializer result may become architecture authority by itself.

## 4. WU-01 — Candidate-discovery evidence expansion

Expand deterministic, reviewable repository evidence collection without assigning final lifecycle ownership.

Key boundary:

```text
repository observation
    -> candidate evidence
    -> selector / candidate identity
    -> later analysis

repository observation
    -X-> automatic lifecycle classification
    -X-> automatic architecture mutation
```

## 5. WU-02 — Evidence/provenance normalization

Normalize equivalent observations from different adapters, preserve origin and ambiguity, strengthen boundary evidence, and provide deterministic inputs for later migration analysis.

Evidence kind and provenance remain separate concerns. `DECLARED`, `OBSERVED`, and `INFERRED` provenance must not be confused with architecture authority.

Detailed plan:

```text
planning/0.3.6.1/WU-02-evidence-provenance-normalization.md
```

## 6. WU-03 — Tool 0.3.5 legacy reader

Introduce a dedicated read-only compatibility boundary for historical Tool `0.3.5` profiles.

Historical classifications are preserved exactly:

```text

TOOLCHAIN
NEUTRAL_CONTRACT
```

The reader must not silently translate `TOOLCHAIN -> DEVELOPMENT_TOOLING` or make legacy state canonical current runtime state.

Detailed plan:

## 7. WU-04 — Lifecycle migration analyzer

Compare legacy architecture, normalized current repository evidence, and the Tool `0.3.6` lifecycle ontology.

The analyzer distinguishes semantic preservation, ambiguous legacy Toolchain cases, possible lifecycle separation, stale declarations, missing relationships/artifacts, and new repository candidates.

It produces analysis, not project intent and not writes.

Detailed plan:

```text
planning/0.3.6.1/WU-04-lifecycle-migration-analyzer.md
```

## 8. WU-05 — Target proposals

Transform migration findings into deterministic, non-mutating, reviewable target-architecture proposals.

Proposal categories may include:

- lifecycle classification;
- component split or justified merge;
- typed relationships;
- associated artifacts;
- selector/include changes;
- explicit unresolved questions and alternatives.

A proposal is not an accepted architecture decision.

Detailed plan:

```text
planning/0.3.6.1/WU-05-target-proposals.md
```

## 9. WU-06 — Preview, confirmation, and safe apply

WU-06 owns the final migration interaction and mutation boundary:

```text
migration proposal
    -> deterministic preview
    -> project-owner confirmation
    -> stale-state / snapshot validation
    -> minimum authorized target delta
    -> safe apply
```

Requirements include:

- preview before mutation;
- explicit confirmation for architecture decisions;
- exact repository/profile snapshot identity;
- fail-closed behavior on stale or conflicting state;
- no blind legacy `TOOLCHAIN` translation;
- no unrelated profile rewrite;
- exact template identity preservation where template/hybrid state is involved;
- deterministic post-apply validation.

A detailed WU-06 stage document is intentionally not pre-created because no prior canonical Tool `0.3.6` WU-10 sub-document existed at the planning split baseline. It should be created only at actual WU-06 entry unless the maintainer explicitly decides otherwise.

## 10. Entry discipline

Tool `0.3.6.1` implementation MUST NOT begin merely because these roadmap documents exist.

Normal entry sequence is:

```text
Tool 0.3.6 released
    -> fresh released/main baseline
    -> confirm Tool 0.3.6.1 Specification family/revision
    -> enter WU-01 with exact baseline
    -> one active WU at a time
```

Each detailed WU document is a planning record until its status is explicitly changed to `ACTIVE` with a fresh exact entry SHA.

## 11. Compatibility and authority invariants

Tool `0.3.6.1` must preserve these invariants from Tool `0.3.6`:

- canonical lifecycle ownership remains project-owned architecture intent;
- discovery and migration evidence are non-authoritative;
- template selection remains explicit and revision-bound;
- Effective Responsibility Map materialization remains deterministic and non-authoritative;
- accepted project decisions authorize only the exact represented delta;
- VPMS Verification Purpose remains a separate axis;
- legacy input is inspected/migrated rather than silently reinterpreted as canonical current architecture.

## 12. Completion boundary

Tool `0.3.6.1` migration development is complete only when:

- candidate discovery is deterministic and provenance-bearing;
- normalized evidence is reviewable and snapshot-bound;
- supported Tool `0.3.5` architecture can be read non-destructively;
- migration analysis preserves ambiguity and historical meaning;
- target proposals are deterministic, explainable, and non-mutating;
- project-owner preview/confirmation is explicit;
- safe apply performs only the accepted target delta and fails closed on stale/conflicting state;
- repository dogfood and required regression/package verification for the migration feature succeed;
- the final Tool/Specification binding is frozen at release time.
