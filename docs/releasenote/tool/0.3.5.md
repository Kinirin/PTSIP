# PTSIP Reference Tool 0.3.5 Release Notes

**Status:** GitHub Release draft prepared; publication pending  
**Tool version:** `0.3.5`  
**Bound Specification:** `0.3.4-draft` @ `b5b17dd16667cc1afaf1d23054b6e5dd773e3f5e`  
**Primary change:** first Tool release to introduce **VPMS — Verification Purpose Management System**

PTSIP Tool `0.3.5` introduces VPMS as a new, independent verification-purpose management subsystem. VPMS did not exist as a shipped Tool subsystem in the preceding Tool line, so this release is not a routine maintenance patch: it adds a second purpose-first management layer beside PTSIP for repositories that need to distinguish why verification exists, reuse verification logic safely, and avoid running unrelated verification work by default.

PTSIP continues to answer:

```text
What is this component?
```

VPMS adds the separate question:

```text
Why does this verification exist?
```

The two systems are intentionally related but not interchangeable. PTSIP remains responsible for Product, Toolchain, and neutral-contract architecture ownership and conformance. VPMS manages verification purpose, composition, selection, and execution. VPMS is **not** a fourth PTSIP Plane and VPMS success is **not** a PTSIP conformance claim.

## Why VPMS was added

Long-lived repositories tend to accumulate many kinds of checks under one broad test surface: Product behavior tests, development-tool verification, packaging checks, release checks, migration checks, repository automation checks, compatibility checks, and policy assertions. When all of them are treated as one undifferentiated suite, three problems appear:

1. verification scope grows even when a change affects only one responsibility;
2. the original reason a verification exists becomes difficult to recover from its path or test implementation;
3. reuse can accidentally erase ownership meaning when shared verification logic is treated as more important than purpose.

VPMS addresses those problems by making verification purpose explicit before selection and execution. Tool `0.3.5` deliberately starts with exactly two verification purposes:

```text
PRODUCT
TOOLCHAIN
```

This purpose is independent from the PTSIP classification of the verification implementation itself. A verifier can be a Toolchain-owned development artifact while protecting Product behavior:

```text
PTSIP classification of verifier = TOOLCHAIN
VPMS verification purpose        = PRODUCT
```

That distinction is central to the design. VPMS does not infer verification purpose from whether a test file is shipped, compiled, or stored under a particular directory.

## Verification Case model

The smallest purpose-bound VPMS execution unit is a **Verification Case**, not a source test file.

A case binds the following semantic units:

- **Purpose** — why the verification exists: `PRODUCT` or `TOOLCHAIN`;
- **Target** — the component or responsibility being protected;
- **Formula** — reusable verification logic or invariant;
- **Variables** — mutable inputs, fixtures, field sets, and case data;
- **Policy** — intentionally governed expectations or contracts;
- **Runner** — the execution adapter used to perform the case.

Conceptually:

```text
Verification Case
    Purpose
    Target
    Formula
    Variables
    Policy
    Runner
```

This separation lets one Formula be reused by multiple cases without merging their purpose, policy, or mutable data.

## Reuse without purpose collapse

Tool `0.3.5` establishes the **Formula** layer as the default cross-purpose reuse boundary.

A reusable Formula should express an invariant that remains meaningful even when Product and Toolchain names are removed from the repository context. Purpose-owned Variables, Policy, and Case bindings remain separate.

This means a Product-purpose case and a Toolchain-purpose case may reuse the same Formula while still remaining different verification obligations:

```text
PRODUCT Case ----\
                  >---- shared Formula
TOOLCHAIN Case --/
```

Reuse therefore does not imply shared purpose, shared policy, or shared execution selection.

## Purpose-based selection and execution

VPMS `0.3.5` implements purpose-based case selection so Product-purpose and Toolchain-purpose verification can be selected independently.

The intended execution model is:

```text
Product-focused change
    -> select PRODUCT-purpose cases

Toolchain-focused change
    -> select TOOLCHAIN-purpose cases

release or explicit full verification
    -> select both purpose sets
```

Selection operates on Verification Case metadata rather than directory names. Sharing a Formula does not force both purpose sets to execute together.

The initial execution layer is intentionally framework-neutral. VPMS provides a generic command adapter rather than making pytest, Jest, Pester, Cargo, Go, or another test framework part of the core model. Framework-specific adapters can be added later only when a concrete requirement justifies them.

## Independent VPMS subsystem

VPMS is shipped as a sibling package under `src/vpms/` rather than as a nested PTSIP implementation module:

```text
src/
├─ ptsip/
└─ vpms/
```

The dependency direction is intentionally one-way:

```text
PTSIP stable metadata
        |
        v
      VPMS
```

PTSIP core **must not depend on VPMS**. PTSIP remains usable for classification, validation, conformance, adoption, gate, resolve, and authority operations when VPMS is absent or unused.

Where VPMS needs PTSIP component information, Tool `0.3.5` uses a narrow read-only bridge instead of importing unstable PTSIP internals. This keeps the two responsibility domains separable and prevents VPMS from becoming a hidden runtime dependency of PTSIP.

## VPMS capabilities delivered in Tool 0.3.5

The first VPMS release includes:

- canonical immutable domain models for Purpose, Target, Formula, Variables, Policy, Runner, and Verification Case;
- registry definition validation with deterministic rejection of malformed definitions;
- reusable Formula registration and lookup;
- purpose-based case selection;
- generic command execution through a framework-neutral adapter;
- selective execution that preserves case identity, purpose, target, and result;
- a read-only PTSIP metadata integration boundary;
- public Python imports for the intentionally supported VPMS surface;
- architecture tests proving PTSIP core does not acquire a VPMS dependency.

Tool `0.3.5` intentionally does **not** add a `vpms` command-line interface. The first public surface is Python-level so the model and package boundary can stabilize before a separate CLI contract is introduced.

## Repository self-adoption

PTSIP now uses VPMS against representative verification responsibilities in its own repository instead of shipping VPMS only as an abstract library.

The initial self-adoption demonstrates both verification purposes and purpose-preserving reuse. Representative cases cover Product distribution/package integrity and Toolchain release/CI integrity while allowing reusable command-exit Formula logic to remain purpose-neutral.

The initial policy identities are:

```text
distribution.contract-integrity
distribution.package-integrity
release.workflow-integrity
ci.verification-boundary
```

The shared Formula identity is:

```text
command.exit-zero
```

These names make the protected responsibility visible without deriving purpose from file-system location.

## Repository self-profile

Tool `0.3.5` also adds a root `ptsip.yaml` self-profile so the PTSIP repository itself is no longer an undeclared consumer of its own architecture policy.

The profile declares Product, Toolchain, and neutral-contract responsibilities for the current repository and is pinned to the active Specification revision. The profile is exercised by dedicated regression tests and by PTSIP validation/clarification/gate flows.

During final release preparation, the self-profile test correctly detected a newly added GitHub Issue Form that was outside all declared selectors. The profile was fixed by assigning `.github/ISSUE_TEMPLATE/**` to repository maintenance rather than weakening the test. The final complete local regression after that correction was:

```text
244 passed
```

This is an intentional example of the self-profile acting as a repository maintenance guard rather than a decorative configuration file.

## Packaging and distribution

Tool `0.3.5` updates package discovery so both `ptsip*` and `vpms*` packages are included in Python distributions.

Release verification covered wheel and sdist construction, package-content checks, installed-wheel smoke checks, Tool/Specification identity, and the absence of an unintended VPMS CLI entry point. VPMS source is distributed as part of the PTSIP Python package release while remaining architecturally independent from PTSIP core.

Canonical installation remains:

```bash
python -m pip install PTSIP
```

Upgrade to the latest published Tool release with:

```bash
python -m pip install --upgrade PTSIP
```

The `0.3.5` release preparation path also exposed two release-note automation defects before publication:

## Compatibility and non-goals

Tool `0.3.5` preserves the existing PTSIP architectural boundary. In particular:

- VPMS is not a fourth PTSIP Plane;
- VPMS does not replace PTSIP conformance;
- VPMS purpose is not inferred from directory layout;
- verification implementation classification and verification purpose remain separate axes;
- Formula reuse does not merge Product and Toolchain policy;
- PTSIP core does not depend on VPMS;
- no mandatory repository test-directory topology is introduced;
- no framework-specific test runner is required;
- no VPMS CLI is introduced in this release.

A VPMS case passing means that the selected verification obligation passed. It does not, by itself, mean the repository is PTSIP conformant. Likewise, PTSIP conformance does not imply Product functional verification has passed.

## Publication boundary

At the time this note is finalized, the GitHub Release for `tool-v0.3.5` is still a draft. Publishing that draft is the explicit publication boundary. The existing Tool release workflow then builds the Python distributions and publishes `PTSIP==0.3.5` through PyPI Trusted Publishing after its release checks succeed.

Tool `0.3.5` should therefore be understood as the **first public VPMS-capable PTSIP Tool release**, not as a maintenance patch that merely exposes previously existing VPMS functionality.
