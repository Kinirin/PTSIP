# PTSIP Tool 0.3.8a5

## Release state and purpose

`0.3.8a5` is the foundation-consolidation prerelease candidate prepared after the published `tool-v0.3.8a4` baseline. Publication is pending. This record describes the changes being integrated from `dev/0.3.8` into `main`; it does not report a completed GitHub Release or PyPI publication.

The candidate closes the approved Context/Evidence verification and independent native-engine foundation work. It preserves existing consumer APIs while preparing explicit contracts, current-policy routing, and evidence for later consumer deployment and versioned handoff.

## Release highlights at a glance

| Responsibility | Published `0.3.8a4` baseline | `0.3.8a5` source candidate |
| --- | --- | --- |
| Developer control plane | Native Go release, policy and verification control | Current-policy Context/Evidence P0/P1 verification plus registered Check coverage |
| Official native engines | No claim of seven independent engine foundations | Seven independently packaged Rust implementations with registered versioned JSON/stdio contracts |
| Verification | Independent exact-source release responsibilities | Required Check registration, source binding and Linux/Windows/macOS native-engine tests |
| Consumer compatibility | Existing Context Plane / VPMS APIs | Existing APIs preserved; production authority admission, activation and consumer cutover remain separate |

These are Tool implementation and verification changes. They do **not** silently amend the `0.3.7-draft` Specification family, `pp.1.02` Project Profile contract, or current consumer authority.
## Current policy and developer-control-plane foundations

- Current Developer and Support Feature policy uses the approved `NORM`, `GOV`, `INTENT`, `ARCH`, `INFO`, `CNTR`, `RISK`, `SUPPLY`, `REAL`, `ASSURE`, `CTRL`, `CHANGE`, `OPS`, and `RECORD` families. Expired family identities and archived policy bodies do not supply current executable authority.
- Current Root policy discovery and lookup is separated from historical reconstruction. Withdrawal of the old VPMS verification identity remains explicit and fail-closed; current native verification uses registered current contracts and owners.
- Go developer automation and verification resolves policy, planning, and binding responsibilities through current machine entries. Policy-plan binding, PRA lifecycle, and current-versus-historical relation checks retain their separate ownership.
- WU-01 and WU-01-P01 close the approved current-policy P0/P1 Context/Evidence read-only verification scope, including source fingerprints, explicit bindings, closed-schema positive/negative cases, and preserved mandatory checks. The candidate does not activate its DRAFT Support policies.

## Seven independent native engines

Seven official engines now have independently built and packaged Rust implementations, versioned JSON capability contracts, and explicit native entrypoint bindings. They expose 27 registered operations. Their implementations do not import another official engine's Rust implementation or delegate to the legacy PTSIP Python runtime.

- **Context** loads identity/version/digest-bound JSON sources, validates declared inline constraints, and preserves source content and provenance in snapshots.
- **Storage** verifies registered provider-operation mediation and current provider/consumer evidence before invoking a separately owned native provider.
- **Validation** provides independent schema, contract, typed-I/O, precondition, and case checks; optional composition; current case-catalog/selector preparation; and preflight of every selected adapter before invocation.
- **Discovery** verifies current source closures and native invocation bindings/artifacts. Derived lookup results remain non-authoritative, and stale or ambiguous affected registrations fail closed.
- **Planning** orders explicit dependency graphs, assesses impact from current two-sided evidence, checks independent package selection, and prepares registered native invocation plans.
- **Execution** invokes exact registered native requests after consuming current caller-admitted local authority. It bounds I/O and time, detects authority changes, and records separate attempt and direct-child stop results. Failure or stop does not establish absence or reversal of work effects.
- **Projection** verifies Context snapshots against their current sources and applies declared output fields, JSON/text formats, and output schemas without changing source semantics.

Context and Projection implementation versions are `0.2.0`, with capability contracts `2.0.0`. Storage, Validation, Discovery, Planning, and Execution implementation versions are `0.3.0`, with capability contracts `3.0.0`. Capability identities and compatibility remain explicit in `src/ptsip/engines/index.json` and the individual engine manifests.

## Verification and packaging

- Registered Check execution and required coverage replace implicit grouped-job success claims. Existing mandatory verification remains independently selectable and accountable to the exact source SHA.
- The native engine Check runs on Linux x64, Windows x64/MSVC, and macOS arm64. Required platform failures block selected native-engine coverage; skipped jobs are not passing evidence.
- Native Go tests exercise actual source loading, transformation, case selection/preflight, registered engine calls, provider-owned file effects, denied/expired/self-issued authority, stale artifacts, timeout, in-flight revocation, and output limits.
- Each independent Cargo package is tested, built, packaged, and exercised over its declared stdio interface. Python distributions include neutral engine contract data; Rust sources/build outputs/native binaries and `profiles/history` are excluded from the wheel.
- The canonical release-note root remains `docs/releasenote/`, with separate Tool, Project Profile, and Specification namespaces.

The implementation baseline `704106b78be4c5cb2296a84c51be97feec1c1494` passed [tooling-test run 38184145188](https://github.com/Kinirin/PTSIP/actions/runs/38184145188): 57 required Checks and 61 successful jobs including native platforms, resolution, and coverage, with zero failures and zero skipped jobs. Linux, Windows, and macOS each executed the full native engine suite. This evidence applies to that implementation SHA; the final integration candidate and `main` are independently verified before release claims.

## Preserved APIs and remaining consumer scope

Existing Consumer Context Plane and VPMS public APIs and their current contracts remain available. New Validation mapping describes explicit validation coverage and responsibility classification; it does not establish full legacy runtime equivalence or retire an API.

The native execution verification scope uses isolated repositories with separately caller-admitted local authority sources. The engines consume those sources without issuing permission or establishing global Project Authority legitimacy. Direct-child process isolation, environment clearing, and I/O/time limits do not provide an OS sandbox or confirm that descendants have stopped.

The following work remains governed by current index-registered `src/policy/` policies, excluding `src/policy/legacy/`:

- Consumer Project Authority legitimacy and required distributed-authority admission/freshness.
- Operator-approved production installation and activation under applicable contract, compatibility, and permission gates.
- Versioned consumer/callsite handoff after behavior and compatibility verification.
- Legacy API retirement after separate explicit owner authorization and required migration evidence.

ACTIVE policy provides current authority. DRAFT policy provides design direction, and RETIRED policy supplies no current execution authority. Startup automatic-activation details in `SFP-CTRL-0002` remain DRAFT. Repository-local Task/runtime namespaces remain reserved; this prerelease does not activate them through implementation availability.

## Consumer migration and deliberate non-goals

- Canonical Tool `0.3.8a5` lifecycle classifications are `PRODUCT`, `DEVELOPMENT_TOOLING`, `DELIVERY`, `OPERATIONS`, and `NEUTRAL_CONTRACT`. Historical `TOOLCHAIN` is migration evidence, not a canonical alias or an automatic conversion into `DEVELOPMENT_TOOLING`.
- The active repository-local Project Profile is selected through `.ptsip/profiles/index.json`. A root `ptsip.yaml` is a legacy compatibility input, not a second current ownership authority; a materialized Effective Responsibility Map cannot invent an owner decision.
- Registered engine contracts and Rust sources do not imply that native binaries ship in the Python wheel or are automatically installed and activated on consumer machines. Neutral engine contract data is packaged separately from engine build artifacts.
- Existing Context Plane and VPMS public API contracts remain available. VPMS Verification Purpose is distinct from lifecycle classification and cannot independently establish PTSIP conformance.
- A caller-authorized native invocation does not confer global Project Authority. Production installation, activation, legacy API retirement, and versioned consumer handoff require their own explicit approval and verification.

No implicit migration, policy activation, compatibility alias or consumer cutover is authorized by this release record.
