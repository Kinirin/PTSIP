# PTSIP Reference Tool 0.3.4 Release Notes

**Status:** Implementation candidate; not yet tagged/published  
**Previous Tool source:** `0.3.3` (permanently source-only)  
**Bound Specification:** `0.2.0-draft` revision `a877b2f66a7f94c1b844c979e1b08fb08a9a8e45`  
**Publication:** no `tool-v0.3.4` tag, GitHub Release, or PyPI publication is created by the implementation merge itself

Tool `0.3.4` completes the GitHub-coordinated repository-global decision-authority consistency contract that was only prototyped in the `0.3.3` source tree.

## Authority freshness at gate time

For GitHub-coordinated repositories, `ptsip gate` now checks the relevant GitHub authority scope even when the selected local Project Profile already contains a complete declaration.

A local declaration therefore cannot cause an early `NO_DECISION_REQUIRED` result without accounting for an existing repository-global authority record for the same normalized component scope.

Authority lookup uses a read-only `peek` path. When `refs/heads/ptsip-policy` does not exist, the lookup does not create the branch or fabricate decision history merely to confirm that no distributed decision exists.

## Reconciliation matrix

Tool `0.3.4` distinguishes the important local/remote states explicitly:

- local declaration absent + no authority decision: create/reuse a pending decision only when the active gate actually requires one;
- local declaration absent + resolved authority winner: validate and safely project the winner into the selected local profile;
- local declaration present + no authority decision: retain the project declaration and return `NO_DECISION_REQUIRED` without fabricating authority history;
- local declaration equivalent + resolved authority winner: return a resolved consistency result without rewriting the profile;
- local declaration conflicting + resolved authority winner: return `AUTHORITY_PROFILE_CONFLICT` and do not silently overwrite/reclassify the Project Profile;
- repository/profile changes during reconciliation: refuse stale application rather than writing over changed local state.

Equivalent profile comparison is semantic rather than YAML-format-sensitive.

## Global decision state vs local projection state

GitHub authority records own global decision state (`PENDING` / `RESOLVED`). They no longer use a single global application flag to imply that every clone has applied the decision.

A clone-local application receipt is reported as:

```text
scope = LOCAL_PROJECTION
status = LOCAL_APPLIED | FAILED | STALE
```

This receipt does not change which architecture answer won and does not claim that other clones have received the profile projection.

## Adoption and resolution

`ptsip adopt --apply` continues to coordinate new GitHub architecture decisions before local mutation. A different resolved winner cannot be overwritten.

If a component is already declared locally and no GitHub authority decision exists, adoption does not create a remote pending decision solely for historical bookkeeping. Existing coordinated pending/resolved authority state is still respected when present.

`ptsip resolve` retains first-valid-resolution-wins semantics. GitHub branch/revision metadata does not create a second global decision identity for the same normalized component scope.

## Fail-closed behavior

Selected GitHub coordination continues to fail closed on unavailable authentication/network/authority state and never silently falls back to a separate Local DecisionStore winner.

Machine-readable coordinated failures now expose `COORDINATION_UNAVAILABLE` where required by the Tool `0.3.4` authority contract.

## Preserved backends and non-goals

Tool `0.3.4` preserves:

- explicit `--coordination local` Local DecisionStore behavior;
- explicit hosted `--control-plane <URL>` behavior;
- no continuous/background authority polling;
- project ownership of `ptsip.yaml`;
- Local SQLite outside the Consumer Repository;
- the three classifications `PRODUCT`, `TOOLCHAIN`, and `NEUTRAL_CONTRACT`;
- deterministic no-LLM clarification and explicit human architecture decisions.

Tool `0.3.4` does not silently bind to the separately proposed Specification `0.3.3-draft` design record. Its active binding remains the immutable `0.2.0-draft` revision above unless a separate coherent Specification decision changes it.

## Verification boundary

Before Tool `0.3.4` is considered a publication candidate, the release boundary requires:

- complete pytest regression coverage, including stale-complete-profile authority freshness and explicit local/remote conflict handling;
- Tool/package version identity checks;
- exact bound Specification identity checks;
- CLI smoke checks;
- wheel and sdist build;
- `twine check`;
- installed-wheel smoke verification.

Tool `0.3.3` remains permanently without a tag, GitHub Release, or PyPI publication. Tool `0.3.4` is the next version eligible for a publication decision only after the verification boundary succeeds.
