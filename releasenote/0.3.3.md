# PTSIP Reference Tool 0.3.3 Release Notes

**Status:** Migration source, not yet published/tagged  
**Expected release tag:** `tool-v0.3.3`  
**Bound Specification:** `0.2.0-draft` revision `a877b2f66a7f94c1b844c979e1b08fb08a9a8e45`

Tool 0.3.3 adds an explicit first-adoption workflow and closes the multi-environment coordination gap left by a purely local DecisionStore, without changing the three PTSIP architecture classifications or the bound Specification revision.

## Explicit project adoption

A new command establishes or extends a project-owned PTSIP declaration from a component candidate discovered by the existing inspection pipeline:

```powershell
ptsip adopt . `
  --component tools `
  --classification TOOLCHAIN `
  --purpose "Repository-local generation tooling" `
  --shipped no `
  --runtime-required no `
  --lifecycle-owner DEVELOPMENT_TOOLING `
  --executable yes `
  --json
```

The default is a read-only dry-run. Repository mutation requires explicit `--apply`.

`ptsip adopt` reuses the existing `DecisionAnswer`, deterministic `validate_answer()` rules, profile projection, schema validation, concurrent-profile guard, and atomic profile writer. It does not infer Product/Toolchain/Neutral ownership from directory names.

The adoption flow checks the discovered candidate identity and repository snapshot, validates the declaration, projects and validates the Project Profile, and refuses stale repository evidence or conflicting existing declarations.

## Profile-path symmetry

Tool 0.3.3 adds `--profile <path>` to:

- `ptsip clarify`;
- `ptsip gate`.

Together with existing support in `adopt`, `resolve`, `validate`, and `conform`, the same project-owned profile location can now be used consistently across the declaration and decision workflow.

Repository-root `ptsip.yaml` remains the default when no explicit profile path is selected.

## GitHub-coordinated decision authority

Local SQLite remains appropriate for a local-only repository, but separate `control-plane.sqlite3` files cannot safely coordinate one still-pending architecture decision across multiple clones or cloud agents.

For repositories with a GitHub origin, Tool 0.3.3 therefore uses a repository-scoped GitHub authority by default:

```text
refs/heads/ptsip-policy
```

The authority ref is bootstrapped automatically by the first write-enabled GitHub-coordinated decision operation. It stores small JSON authority/decision documents; it never stores or synchronizes SQLite.

Decision mutations use Git object creation followed by a non-force ref update. A writer that observed an older authority HEAD cannot overwrite a newer winner. PTSIP retries against the new authority state instead.

Global `gdec-*` identity is derived from GitHub repository identity plus normalized discovered include selectors. It is intentionally independent of one clone's local clarification ID, branch, or missing-field set, preventing temporarily divergent Project Profiles from creating separate winners for the same component scope.

## Action-time reconciliation

PTSIP does not introduce continuous background polling.

If a stale clone's selected Project Profile is missing a declaration but the GitHub authority already contains a resolved winner, `ptsip gate` reconciles that answer into the local profile and returns a resolved result. This allows a cloud/local agent to observe an accepted decision before another environment has committed and pushed its `ptsip.yaml` projection.

`ptsip.yaml` remains the project-owned architecture declaration for repository revisions. The GitHub authority exists to coordinate unresolved/resolved decision workflow state between environments.

## Backend selection and fail-closed behavior

The built-in selection order is:

```text
--control-plane <URL>     -> explicit hosted HTTP Control Plane
--coordination local      -> explicit Local DecisionStore
--coordination github     -> explicit GitHub authority
GitHub origin detected    -> GitHub authority
otherwise                 -> Local DecisionStore
```

`--control-plane` and `--coordination` are mutually exclusive.

GitHub-coordinated operations authenticate with `GH_TOKEN` or `GITHUB_TOKEN`, or fall back to an authenticated `gh` CLI on interactive machines. The credential must be able to update repository Git refs/contents.

If GitHub coordination is selected but unavailable, PTSIP blocks the new architecture-decision operation. It does **not** silently fall back to Local SQLite, because that would create split-brain first-winner state.

## Local state and Git ownership

Local decision state remains external to the Consumer Repository under `PTSIP_HOME`, for example on Windows:

```text
%LOCALAPPDATA%\PTSIP\decisions\<repository-fingerprint>\control-plane.sqlite3
```

`control-plane.sqlite3` is operational Tool state and should not be committed or shared through Git.

The default project architecture declaration remains:

```text
<repository-root>/ptsip.yaml
```

That profile is intended to be committed with the Consumer Repository rather than added to `.gitignore`.

## Specification-binding boundary

The explicit `DecisionAnswer.runtime_required` fact remains part of decision/adoption validation and is retained in GitHub authority records. Tool 0.3.3 does not add a new `runtime_required` field to the bound Project Profile schema, because doing so would silently widen the immutable `0.2.0-draft` revision contract.

Any future Project Profile schema change for that fact requires an explicit Specification revision decision rather than a Tool-only schema drift.

## Hosted Control Plane compatibility

The GitHub App/Webhook service introduced in Tool 0.3.1 remains available as an explicit hosted backend through:

```powershell
ptsip gate . --control-plane https://control-plane.example --json
```

The embedded Local DecisionStore and the GitHub-coordinated authority do not remove that integration surface.

## Regression boundary

Tool 0.3.3 does not change:

- the PTSIP Specification family or bound immutable revision;
- the three architecture classifications: `PRODUCT`, `TOOLCHAIN`, `NEUTRAL_CONTRACT`;
- conformance outcomes or universal rule semantics;
- deterministic clarification's zero-LLM behavior;
- Tool 0.3.2 topology classification-preservation behavior;
- project ownership of `ptsip.yaml`;
- the rule that a coding agent must not invent missing architecture intent.

Global `gate --json` exception-envelope redesign and aggregate gate-precondition diagnostics remain separate follow-up work rather than being silently folded into this migration.
