# PTSIP Reference Tool 0.3.3 Release Notes

**Status:** Completed source-only migration; permanently unpublished and untagged  
**Publication decision:** no `tool-v0.3.3` tag, no GitHub Release, and no PyPI `PTSIP==0.3.3` publication will be created  
**Next Tool publication candidate:** `0.3.4`  
**Bound Specification:** `0.2.0-draft` revision `a877b2f66a7f94c1b844c979e1b08fb08a9a8e45`

Tool `0.3.3` completes the explicit first-adoption workstream and Project Profile path symmetry without changing the three PTSIP architecture classifications or its bound Specification revision.

During the same source migration, an initial GitHub-coordinated authority prototype was also implemented. The previously approved Tool `0.3.3` authority amendment has since been withdrawn from the `0.3.3` completion scope because repository-global read freshness, existing-declaration reconciliation, conflict semantics, and the global-versus-local application-state model still require a coherent completion pass.

That distributed-authority work continues as the independent Tool `0.3.4` workstream in:

```text
planning/PTSIP-TOOL-0.3.4-GITHUB-COORDINATED-AUTHORITY-PLAN.md
```

## Explicit project adoption

Tool `0.3.3` adds an explicit project-owner path for establishing or extending a PTSIP Project Profile from a discovered component candidate:

```powershell
ptsip adopt . `
  --component tools `
  --classification TOOLCHAIN `
  --purpose "Repository-local generation tooling" `
  --shipped no `
  --runtime-required no `
  --lifecycle-owner DEVELOPMENT_TOOLING `
  --executable yes `
  --json
```

The default is a read-only dry-run. Repository mutation requires explicit `--apply`.

`ptsip adopt` reuses the existing `DecisionAnswer`, deterministic `validate_answer()` rules, Project Profile projection, schema validation, concurrent-profile guard, and atomic profile writer. It does not infer Product/Toolchain/Neutral ownership from directory names.

The adoption flow checks the discovered candidate identity and repository snapshot, validates the supplied declaration, prepares and validates the projected Project Profile, and refuses stale evidence or conflicting existing declarations.

## Profile-path symmetry

Tool `0.3.3` adds `--profile <path>` support to:

- `ptsip clarify`;
- `ptsip gate`.

Together with existing support in `adopt`, `resolve`, `validate`, and `conform`, the same project-owned profile location can be selected consistently throughout the declaration and decision workflow.

Repository-root `ptsip.yaml` remains the default when no explicit profile path is supplied.

## Local DecisionStore continuity

Local decision state remains external to the Consumer Repository under `PTSIP_HOME`, for example on Windows:

```text
%LOCALAPPDATA%\PTSIP\decisions\<repository-fingerprint>\control-plane.sqlite3
```

`control-plane.sqlite3` is Tool-owned operational state and must not be committed or shared through Git.

The existing explicit hosted HTTP Control Plane remains supported where selected by the decision workflow.

## Experimental GitHub authority prototype

The `0.3.3` source tree contains an initial GitHub-coordinated authority implementation developed while the withdrawn authority amendment was being evaluated.

The prototype includes useful foundations such as:

- repository-scoped `refs/heads/ptsip-policy` authority state;
- `authority.json` ownership validation;
- global `gdec-*` identity derived from repository identity plus normalized include scope;
- non-force Git ref compare-and-swap writes;
- first-winner protection for contradictory concurrent writes;
- basic stale-clone projection when the local declaration is absent;
- fail-closed behavior instead of silent Local SQLite fallback when GitHub coordination is selected.

These foundations are retained as precursor implementation for Tool `0.3.4`. They are **not** treated as proof that Tool `0.3.3` completed the full repository-global distributed-authority contract.

In particular, Tool `0.3.3` does not claim release-quality completion of:

- authority freshness when a local Project Profile already contains a declaration;
- deterministic local-versus-remote conflict reconciliation;
- final machine-readable authority/profile conflict semantics;
- final global decision versus clone-local application-state semantics;
- complete multi-clone distributed consistency verification.

## Project Profile ownership

The default project architecture declaration remains:

```text
<repository-root>/ptsip.yaml
```

The Project Profile is project-owned and intended to be committed with the Consumer Repository rather than added to `.gitignore`.

The experimental GitHub authority prototype does not replace the Project Profile.

## Specification-binding boundary

Tool `0.3.3` remains bound to immutable Specification revision:

```text
0.2.0-draft
a877b2f66a7f94c1b844c979e1b08fb08a9a8e45
```

The separately proposed `0.3.3-draft` Specification family is an independent Specification workstream and does not retroactively rebind Tool `0.3.3`.

The `DecisionAnswer.runtime_required` fact remains part of decision/adoption validation. Tool `0.3.3` does not silently add a new `runtime_required` field to its bound predecessor Project Profile schema.

## Regression boundary

Tool `0.3.3` does not change:

- the three architecture classifications: `PRODUCT`, `TOOLCHAIN`, `NEUTRAL_CONTRACT`;
- conformance outcomes or universal rule semantics;
- deterministic clarification's zero-LLM behavior;
- Tool `0.3.2` topology classification-preservation behavior;
- project ownership of `ptsip.yaml`;
- the rule that a coding agent must not invent missing architecture intent.

Global `gate --json` exception-envelope redesign and aggregate gate-precondition diagnostics remain separate follow-up work except where Tool `0.3.4` may need stable machine-readable authority consistency states.
