# PTSIP Tool 0.3.7

> **State:** Release candidate; final exact-SHA verification and publication pending
> **Project Profile contract:** `pp.1.01`
> **Specification:** `0.3.7-draft @ 3c47816770d194ae42f98faedc911d980db0e62a`

## Independent release identities

Tool `0.3.7` completes the separation of four identities that older profiles
could represent through one Tool-numbered label:

```text
Tool Version:                     0.3.7
Project Profile Contract Version: pp.1.01
Specification family:             0.3.7-draft
Specification revision:           3c47816770d194ae42f98faedc911d980db0e62a
Project Profile Instance Revision: repository/content-specific
```

The Tool version does not imply the Project Profile contract or Specification
revision. `ptsip spec --json` reports the Tool, PP, family, source, and immutable
revision as separate fields.

## Specification binding and validation

- adds typed `SpecificationBinding` values for family, source, and immutable
  revision;
- composes Project Profile and Specification operation capabilities
  independently;
- requires explicit binding fields in current `pp.1.01` profiles;
- keeps supported historical `0.3.6-draft` validation explicit without routing
  generic validation through migration bridges;
- fails closed for malformed or unsupported bindings and capabilities.

## Project Profile compatibility and migration

Tool `0.3.7` introduces the independent `pp.*` contract namespace and selects
`pp.1.01` as its current target. The historical
`0.3.6-draft -> pp.1.01` bridge is `IDENTITY_ONLY`: it changes contract identity
and materializes the explicit historical Specification family while preserving
source, revision, lifecycle classifications, components, relationships,
associated artifacts, and policies.

Historical sources converge directly to the selected current target through
revision-bound compatibility readers, normalized evidence, typed analysis,
deterministic planning, guarded execution, recovery, and promotion. Intermediate
Project Profile generations are not mandatory migration hops.

## Release-candidate identity decoupling closure

The pre-publication release review found residual Tool-numbered draft vocabulary
on the current migration target path. This was corrected before publication:

- the migration analyzer's default target is now selected from the current
  Project Profile capability (`pp.1.01`) rather than from Tool `0.3.7` or the
  `0.3.7-draft` Specification family;
- direct latest-target convergence exposes the target as `profile_contract`
  instead of presenting the current PP identity through the historical
  `draft_version` vocabulary;
- the top-level migration package exposes direct PP convergence and identity
  rewrite as the canonical current migration surface, while the older
  sequential-draft planner remains an internal legacy/continuity implementation;
- historical `0.3.x-draft` source fixtures and accepted legacy temporary-target
  aliases remain intentionally preserved as compatibility evidence. They are not
  current Project Profile target authority;
- Specification family `0.3.7-draft` remains unchanged and independently bound
  to the immutable Specification revision above.

Regression guards now assert that the repository profile keeps `pp.1.01` and
`0.3.7-draft` as separate identities and that current PP migration runtime
surfaces do not hard-code the Specification family as their Project Profile
target.

## Command-faithful validation capture

The new command:

```text
ptsip validation capture -- <command> [args...]
```

executes the literal argument vector exactly once without a shell, captures both
output streams into a timestamped `docs/ptsip/validation/*.log`, creates a local
commit containing only that log, preserves the child exit code, and never pushes
automatically.

## Release boundary

This source note does not claim publication or WU-12 completion. A fresh
self-hosted `tooling-test` run must succeed for the final exact source SHA,
including the complete regression, independent identity contract, root profile,
distribution, Product Artifact, and installed-wheel checks. Release preparation,
maintainer publication, and Trusted Publishing remain separate later actions.
