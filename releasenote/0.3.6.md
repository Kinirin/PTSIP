# PTSIP Tool 0.3.6

> **State:** Release candidate — WU-07 release preparation in progress  
> **Tool/package version:** `0.3.6`  
> **Bound Specification:** `0.3.6-draft @ d6995ed232e845b88d8235b851e80ab54b7804ea`

Tool `0.3.6` introduces the Primary Lifecycle Ownership foundation and Responsibility Map v2. This release separates lifecycle ownership from roles, relationships, declaration provenance, and VPMS Verification Purpose while preserving fail-closed behavior when architecture or evidence is incomplete.

## Primary Lifecycle Ownership

Canonical Tool `0.3.6` classifications are exactly:

```text
PRODUCT
DEVELOPMENT_TOOLING
DELIVERY
OPERATIONS
NEUTRAL_CONTRACT
```

`TOOLCHAIN` remains historical Tool `0.3.5` migration input only. It is not a canonical Tool `0.3.6` classification alias and is not blindly converted to `DEVELOPMENT_TOOLING`.

Classification represents the primary lifecycle ownership of a project responsibility rather than its filename, directory, framework, executable status, workflow provider, or whether the artifact happens to be a test.

## Responsibility Map v2

Responsibility Map v2 separates several independent architecture axes:

- lifecycle `classification`;
- coarse responsibility `roles`;
- typed project-owned `relationships`;
- declaration/materialization provenance;
- VPMS Verification Purpose.

Canonical roles are `IMPLEMENTATION`, `VERIFICATION`, `AUTOMATION`, `CONFIGURATION`, `DOCUMENTATION`, and `GOVERNANCE`.

The map also supports associated artifacts for project-owned non-component support surfaces that remain subordinate to one classified anchor component without inheriting a lifecycle classification.

## Explicit, template, and hybrid declarations

Tool `0.3.6` supports three Responsibility Map source modes:

```text
explicit
template
hybrid
```

Template selection is explicit and immutable-revision-bound. Repository evidence, detected language/framework, layout, manifests, or confidence do not automatically select architecture authority.

Materialization is deterministic and non-authoritative. It resolves the selected project-owned declaration into the effective architecture but does not infer missing lifecycle ownership, silently repair invalid declarations, or rewrite source state merely to produce a valid result.

Hybrid mode preserves the selected immutable template while allowing project-owned stable-ID replacement, extension, and removal decisions.

## Canonical Effective Responsibility Map

All supported source modes resolve to one Canonical Effective Responsibility Map used by downstream Tool behavior.

Validation, conformance, clarification/adoption, and the narrow VPMS integration consume validated resolved architecture rather than independently reinterpreting raw source YAML. The resolved map retains source/template provenance and provides deterministic digest identity for reproducibility without turning that digest into architecture authority.

## Clarification and adoption integration

The clarification/adoption flow now consumes validated effective architecture and fails closed when profile resolution is invalid or ambiguous.

New canonical clarification answers use `ptsip-clarification-answer/v2` and represent `classification`, `purpose`, `shipped`, `runtime_required`, and `executable` without restoring the historical `lifecycle_owner` field as Tool `0.3.6` authority.

An accepted project-owned decision may authorize only the minimum declaration delta required to represent that decision. Where necessary, an accepted decision may transition a template declaration to hybrid while preserving the exact selected template identity and revision. Discovery or materialization alone cannot authorize that write.

The selected repository-relative profile path is preserved through the complete decision protocol, including stale checks and remote CAS handling.

## VPMS compatibility boundary

PTSIP lifecycle classification and VPMS Verification Purpose remain independent.

The packaged VPMS compatibility layer remains a narrow read-only consumer of already-resolved PTSIP metadata. PTSIP core does not depend on VPMS, and VPMS does not become Responsibility Map or lifecycle-classification authority.

The current VPMS purpose vocabulary may continue to expose `PRODUCT | TOOLCHAIN` for compatibility. VPMS `TOOLCHAIN` is not a canonical PTSIP Tool `0.3.6` classification.

## Release contract strengthening

WU-07 strengthens release preparation without redesigning the release pipeline around a new build-once/attestation architecture.

Release-bound Specification assets are checked against the exact immutable `SPEC_REVISION` so release source cannot silently carry modified normative content while claiming an older bound snapshot. Canonical and embedded machine-readable assets must also remain coherent.

The publication workflow rebuilds the release distributions from the published Tool tag on self-hosted Windows and now applies Product Artifact content/evidence and exact-snapshot binding checks to the actual publication wheel before the distributions are uploaded for PyPI Trusted Publishing.

## Compatibility and migration

Tool `0.3.6` intentionally does not ship the evidence-driven Tool `0.3.5 -> 0.3.6` architecture migration pipeline.

That continuation is planned for Tool `0.3.6.1`, including stronger candidate discovery/evidence normalization, legacy Tool `0.3.5` reading, migration analysis, target proposals, owner preview/confirmation, and safe apply.

Tool `0.3.6` therefore establishes the new canonical architecture model and the deterministic effective-map foundation; Tool `0.3.6.1` is responsible for the later assisted migration experience.

## Release process

The final publication boundary remains exact-SHA gated:

```text
merge approved 0.3.6 state to main
    -> run tooling-test.yml on the exact main SHA
    -> require self-hosted/tooling-test success on that SHA
    -> run release.yml from the same current main SHA
    -> verify Tool / Specification / SPEC_REVISION release contract
    -> create reviewed draft GitHub Release for that exact SHA
    -> publish the reviewed draft
    -> tooling-release.yml rebuilds and verifies distributions from the published tag
    -> PyPI Trusted Publishing
```
